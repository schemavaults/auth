# Dynamic Client Registration (RFC 7591) & resource-URL audiences

## Registration endpoint

`POST /api/oidc/register` (`auth-server/src/app/api/oidc/register/route.ts`) is the RFC 7591 §3 registration endpoint: unauthenticated (open registration, no initial access token), JSON in / JSON out, wildcard CORS, `Cache-Control: no-store`. It is **off by default**: the `allow_dynamic_client_registration` server setting (`SERVER_SETTING_DEFINITIONS`, editable on `/admin/settings`) must be `true`, otherwise the endpoint answers 403 `access_denied`. The discovery document (`buildOidcDiscoveryDocument()` → `buildOidcProviderMetadata(issuer, { registration_endpoint })`) advertises `registration_endpoint` (`OIDC_ENDPOINT_PATHS.registration`) only while the setting is on; the client SDK builds its metadata without it. Registrations are rate limited per IP in their own bucket (`DYNAMIC_CLIENT_REGISTRATION_RATE_LIMIT`, 10/hour) and the body is capped at 128 KiB.

Request parsing is pure and shared: `parseDynamicClientRegistrationRequest(body, { allow_localhost_redirect_uris, allow_custom_scheme_redirect_uris })` in `packages/auth-common/src/oidc/dynamic-client-registration.ts` (unit tested there). Rules: `redirect_uris` required (deduplicated, ≤50), each `https`, an `http` loopback-IP URI (`127.0.0.1` / `[::1]`, RFC 8252 §7.3), or — per the `dynamic_client_registration_allow_localhost_redirect_uris` / `dynamic_client_registration_allow_custom_scheme_redirect_uris` settings (both default `true`) — `http://localhost` (matched port-exactly) or a private-use scheme (`com.example.app:/cb`, `vscode://…`); violations are `invalid_redirect_uri`. `token_endpoint_auth_method` defaults to `client_secret_basic` (RFC 7591 §2; MCP clients send `none`), only `none`/`client_secret_basic`/`client_secret_post` are accepted; `grant_types` ⊆ {`authorization_code`, `refresh_token`} (must include `authorization_code`), `response_types` = [`code`]; `jwks`, `jwks_uri`, `software_statement` are refused; unknown members are ignored. `client_name` is trimmed and must fit `APP_NAME_MAX_LENGTH` (128; the definition-wide `app_name` cap, raised from 64) — never truncated; absent → derived from the first redirect URI's host. Everything else maps to `invalid_client_metadata`.

`registerDynamicClient()` (`auth-server/src/lib/oidc/dynamic-client-registration/`) persists in **one transaction**: the `APPS` row (`app_id` = `dcr-<uuid>`, `web: true` even for native clients because `validateOidcAuthorizeRequest` refuses `web: false`, `public: false`, `owner_type = 'dynamic-client-registration'`, the RFC 7591 metadata columns), one `APP_CALLBACK_URLS` row per redirect URI for the deployment's own environment (`getAppEnvironment()` — registration has no environment concept), and, for confidential clients, a generated `svs_…` secret hashed into `APP_CLIENT_SECRETS`. The §3.2.1 response echoes all registered metadata plus `client_id`, `client_id_issued_at` (seconds) and, when applicable, the one-time `client_secret` with `client_secret_expires_at: 0`. RFC 7592 management (registration access tokens, PUT/DELETE) is **not** implemented; admins manage registered clients from the console.

## Ownership & storage

`dynamic-client-registration` is the fourth `ResourceOwnerType` (`@schemavaults/app-definitions`, `resource-ownership.ts`; helpers `dynamicClientRegistrationOwnership()`, `isDynamicallyRegisteredClient()`). Migration `00040` adds it to the `APPS` CHECK constraints only (API servers are never registered dynamically), adds the metadata columns (`client_uri`, `logo_uri`, `tos_uri`, `policy_uri`, `contacts`/`grant_types`/`response_types` as JSONB, `token_endpoint_auth_method`, `software_id`, `software_version`, `registered_scope`, `client_id_issued_at`; all in `dynamicClientRegistrationMetadataFieldsShape`, NULL for console-created apps), and adds `allow_dynamic_clients` (default `false`) + `resource_url_match_mode` (`exact` | `prefix`, default `exact`) to `API_SERVERS`. `getUserAccessLevelForOwnership()` maps the owner type to `none` for everyone but global admins, so only admins can view/manage/delete these rows; `resolveRequestedOwnershipForCreation()` refuses it on `POST /api/apps`. The admin app list (`/admin/apps`, and `/apps` for admins) offers a "Dynamic registration" option in `<OwnerTypeFilter showDynamicClientRegistration />`, and `<ResourceOwnerLabel />` renders it. Browser CORS for such clients derives origins from their http(s) callback URLs (`getAppAllowedOriginsForEnvironment`) since they have no `APP_DOMAINS`.

## Resource-URL audiences (RFC 8707) and API server policy

MCP clients send the resource server's **URL** as `resource`. `createAudienceSchema()` (`@schemavaults/auth-common`) now accepts a third form, an absolute http(s) URL (`createResourceUrlAudienceSchema`, `isResourceUrlAudience`), on every surface (token endpoints, JWT generation/decoding, token records). The auth server resolves a URL with `resolveTokenAudience()` / `resolveResourceUrlToApiServer()` (`auth-server/src/lib/oidc/resolve-token-audience.ts`): candidates are the current environment's `api_server_domains` rows whose domain starts with the URL's origin, matched per the owning API server's `resource_url_match_mode` (`doesResourceUrlMatchApiServerDomain()`: `exact` = equals a registered domain, `prefix` = also any `/`-delimited path under it); no match or more than one API server matching → `invalid_target` (`UnresolvableTokenResourceError`). `validateAndResolveAudiences()` (`validate-audience.ts`) then applies the usual rules, except that a dynamically registered client may skip the `apps_to_apis_permissions` check for an API server whose `allow_dynamic_clients` is on — managed clients always need a connection. The grant handlers pass the resolved `{ access_token_audience, api_server_id }` to `issueOidcTokens()` → `generateTokensForAuthenticatedUser({ audience_api_server_ids })` → `generateAccessToken({ token_audience })`: the token's `aud` is **the URL verbatim**, the keyset (and the `issued_tokens.audience` record) is the resolved API server's; `@schemavaults/jwt`'s keyset/audience check tolerates that mismatch for access tokens. Refresh tokens keep the auth server audience, so the refresh grant and introspection are unchanged.

Policy management: `PATCH /api/apis/[api_server_id]` (`allow_dynamic_clients`, `resource_url_match_mode`; `canUserManageResource`), `SchemaVaultsApiServerRegistry.setApiServerDynamicClientPolicy()`, the client SDK's `updateApiServerDynamicClientPolicy()`, and `<ApiServerDynamicClientsCard />` on `/apis/[api_server_id]`. The E2E seed route accepts `allow_dynamic_clients` / `resource_url_match_mode`.

Resource servers built on `@schemavaults/auth-server-sdk` must opt into URL audiences: `RouteGuardFactory({ accepted_audiences: [url] })`, `SchemaVaultsServerMiddleware({ accepted_audiences })`, or `decodeJWTsWithKeyManager(…, { accepted_audiences })`. `resolveExpectedTokenAudience()` reads the presented token's unverified header `aud`; if it is one of the accepted URLs that value is enforced by the decode, otherwise the API server id form is (keysets are always looked up by the id). The example resource server reads `SCHEMAVAULTS_ACCEPTED_TOKEN_AUDIENCES` (comma-separated) in `auth-resolvers.ts`.

## Client SDK & tests

`@schemavaults/auth-client-sdk`: `registerDynamicClient(metadata)` on the client (and the standalone `registerDynamicClient({ adapter, auth_server_uri, metadata })`), throwing `DynamicClientRegistrationFailedError` (`status`, `error`, `error_description`, `isRfc7591Error()`) on refusal; `updateApiServerDynamicClientPolicy(api_server_id, update)`.

E2E: the standalone `dynamic_client_registration` suite (`tests/e2e-auth-tests/cypress/e2e/dynamic_client_registration/`) runs with the example resource server (`suiteNeedsExampleResourceServer()` in `e2e-auth-tests-cli.ts` selects the `e2e_with_resource_server` compose profile and generates JWKS keys; `cypress.config.ts` seeds the example app/API with `allow_dynamic_clients: true, resource_url_match_mode: "prefix"`; docker-compose sets the resource server's `SCHEMAVAULTS_ACCEPTED_TOKEN_AUDIENCES` to `http://example-nextjs-resource-server/api`) and has its own job in `run-e2e-tests.yml`. It toggles the setting through `PATCH /api/admin/settings/allow_dynamic_client_registration` as the superuser and restores it afterwards.
