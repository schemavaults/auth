# Dynamic Client Registration (RFC 7591) & resource-URL audiences

## Registration endpoint

`POST /api/oidc/register` (`auth-server/src/app/api/oidc/register/route.ts`) is the RFC 7591 §3 registration endpoint: unauthenticated (open registration, no initial access token), JSON in / JSON out, wildcard CORS, `Cache-Control: no-store`. It is **off by default**: the `allow_dynamic_client_registration` server setting (`SERVER_SETTING_DEFINITIONS`, editable on `/admin/settings`) must be `true`, otherwise the endpoint answers 403 `access_denied`. The discovery document (`buildOidcDiscoveryDocument()` → `buildOidcProviderMetadata(issuer, { registration_endpoint })`) advertises `registration_endpoint` (`OIDC_ENDPOINT_PATHS.registration`) only while the setting is on; the client SDK builds its metadata without it. Registrations are rate limited per IP in their own bucket (`DYNAMIC_CLIENT_REGISTRATION_RATE_LIMIT`, 10/hour) and the body is capped at 128 KiB.

Request parsing is pure and shared: `parseDynamicClientRegistrationRequest(body, { allow_localhost_redirect_uris, allow_custom_scheme_redirect_uris })` in `packages/auth-common/src/oidc/dynamic-client-registration.ts` (unit tested there). Rules: `redirect_uris` required (deduplicated, ≤50), each `https`, an `http` loopback-IP URI (`127.0.0.1` / `[::1]`, RFC 8252 §7.3), or — per the `dynamic_client_registration_allow_localhost_redirect_uris` / `dynamic_client_registration_allow_custom_scheme_redirect_uris` settings (both default `true`) — `http://localhost` (matched port-exactly) or a private-use scheme (`com.example.app:/cb`, `vscode://…`); violations are `invalid_redirect_uri`. `token_endpoint_auth_method` defaults to `client_secret_basic` (RFC 7591 §2; MCP clients send `none`), only `none`/`client_secret_basic`/`client_secret_post` are accepted; `grant_types` ⊆ {`authorization_code`, `refresh_token`} (must include `authorization_code`; default `["authorization_code"]`) and enforced at the token endpoint (`isGrantTypeAllowedForClientApp()`, `auth-server/src/lib/oauth2/client-grant-types.ts`; `refresh_token` is implied by `authorization_code`, and `client_credentials` is never available to a registered client nor can it have a service account — see the `client-credentials-grant` skill), `response_types` = [`code`]; `jwks`, `jwks_uri`, `software_statement` are refused; unknown members are ignored. `client_name` is trimmed and must fit `APP_NAME_MAX_LENGTH` (128; the definition-wide `app_name` cap, raised from 64) — never truncated; absent → derived from the first redirect URI's host. Everything else maps to `invalid_client_metadata`.

`registerDynamicClient()` (`auth-server/src/lib/oidc/dynamic-client-registration/`) persists in **one transaction**: the `APPS` row (`app_id` = `dcr-<uuid>`, `web: true` even for native clients because `validateOidcAuthorizeRequest` refuses `web: false`, `public: false`, `owner_type = 'dynamic-client-registration'`, the RFC 7591 metadata columns), one `APP_CALLBACK_URLS` row per redirect URI for the deployment's own environment (`getAppEnvironment()` — registration has no environment concept), and, for confidential clients, a generated `svs_…` secret hashed into `APP_CLIENT_SECRETS`. The §3.2.1 response echoes all registered metadata plus `client_id`, `client_id_issued_at` (seconds) and, when applicable, the one-time `client_secret` with `client_secret_expires_at: 0`. RFC 7592 management (registration access tokens, PUT/DELETE) is **not** implemented; admins manage registered clients from the console.

## Ownership & storage

`dynamic-client-registration` is the fourth `ResourceOwnerType` (`@schemavaults/app-definitions`, `resource-ownership.ts`; helpers `dynamicClientRegistrationOwnership()`, `isDynamicallyRegisteredClient()`). Migration `00040` adds it to the `APPS` CHECK constraints only (API servers are never registered dynamically), adds the metadata columns (`client_uri`, `logo_uri`, `tos_uri`, `policy_uri`, `contacts`/`grant_types`/`response_types` as JSONB, `token_endpoint_auth_method`, `software_id`, `software_version`, `registered_scope`, `client_id_issued_at`; all in `dynamicClientRegistrationMetadataFieldsShape`, NULL for console-created apps), and adds `allow_dynamic_clients` (default `false`) + `resource_url_match_mode` (`exact` | `prefix`, default `exact`) to `API_SERVERS`. `getUserAccessLevelForOwnership()` maps the owner type to `none` for everyone but global admins, so only admins can view/manage/delete these rows; `resolveRequestedOwnershipForCreation()` refuses it on `POST /api/apps`. The admin app list (`/admin/apps`, always, and `/apps` for admins while the `allow_dynamic_client_registration` setting is on or such apps are listed) offers a "Dynamic registration" option in `<OwnerTypeFilter showDynamicClientRegistration />`, and `<ResourceOwnerLabel />` renders it. In the apps table, `AppNameCell` marks such a client with `<DynamicClientRegistrationIcon />` (robot, `useIsDynamicallyRegisteredClient()`, both exported by `@schemavaults/auth-ui`) and its registration time, since registrations of the same MCP client all share one self-chosen name. Its `/apps/[client_app_id]` page adds the robot to the title and `<DynamicClientRegistrationMetadataCard />` (`auth-server/src/components/DynamicClientRegistrationMetadata/`), which shows the stored RFC 7591 metadata defensively through `summarizeDynamicClientRegistrationMetadata()` (unit tested): only plain http(s) URLs without embedded credentials become links (new tab, `noopener noreferrer nofollow`, `referrerPolicy="no-referrer"`, punycode host), control and bidi-formatting characters become U+FFFD, and the logo is linked but never loaded. Pinned by the E2E spec `dynamic_client_registration/DynamicClientAdminConsole.cy.ts`. Browser CORS for such clients derives origins from their http(s) callback URLs (`getAppAllowedOriginsForEnvironment`) since they have no `APP_DOMAINS`.

## Resource-URL audiences (RFC 8707) and API server policy

MCP clients send the resource server's **URL** as `resource`. `createAudienceSchema()` (`@schemavaults/auth-common`) now accepts a third form, an absolute http(s) URL (`createResourceUrlAudienceSchema`, `isResourceUrlAudience`), on every surface (token endpoints, JWT generation/decoding, token records). The auth server resolves a URL with `resolveTokenAudience()` / `resolveResourceUrlToApiServer()` (`auth-server/src/lib/oidc/resolve-token-audience.ts`): candidates are the current environment's `api_server_domains` rows whose domain starts with the URL's origin (verified rows first; unverified ones only as a fallback, see below), matched per the owning API server's `resource_url_match_mode` (`doesResourceUrlMatchApiServerDomain()`: `exact` = equals a registered domain, `prefix` = also any `/`-delimited path under it); no match or more than one API server matching → `invalid_target` (`UnresolvableTokenResourceError`). `validateAndResolveAudiences()` (`validate-audience.ts`) then applies the usual rules, except that a dynamically registered client may skip the `apps_to_apis_permissions` check for an API server whose `allow_dynamic_clients` is on — managed clients always need a connection. The grant handlers pass the resolved `{ access_token_audience, api_server_id }` to `issueOidcTokens()` → `generateTokensForAuthenticatedUser({ audience_api_server_ids })` → `generateAccessToken({ token_audience })`: the token's `aud` is **the URL verbatim**, the keyset (and the `issued_tokens.audience` record) is the resolved API server's; `@schemavaults/jwt`'s keyset/audience check tolerates that mismatch for access tokens. Refresh tokens keep the auth server audience, so the refresh grant is unchanged; the API server a resource URL resolved to can introspect the URL-audience access token (`/api/oidc/introspect` with `private_key_jwt`: it decrypts with that server's own keyset, so no URL re-resolution is needed).

**Verified domains take precedence; enforcement is a server setting** (migration 00057, `auth-server/src/lib/api-server-domain-verification/`). Any signed-in user may create an API server and register any domain on it, so `resolveResourceUrlToApiServer()` first matches only `api_server_domains` rows with `verified_at` / `verification_method` set (`findApiServersMatchingResourceUrl({ registrations: "verified" })`, served by a partial index): when one matches, unverified registrations are ignored, so a registration of someone else's origin can neither make it ambiguous nor capture it. Only when no verified domain matches does it fall back to every registration (`registrations: "any"`, the pre-verification behaviour), and only while the `require_api_server_domain_verification` server setting is off (**default off**, so the rollout breaks nothing while owners verify; `requireApiServerDomainVerification()` in `lib/config/`, read only on that fallback path). Turning the setting on makes unverified registrations never resolve. The `/apis/[api_server_id]` page (domain card, badge title, Verify dialog) and the auth-ui add-domain toast word their copy for both modes. Every registration gets its own random `verification_token` on insert (`generateDomainVerificationToken()`; the `ApiServerDomainsTable` columns are not part of the strict `SchemaVaultsApiServerDomainRef`, so `getApiServerDomains()` selects `API_SERVER_DOMAIN_REF_COLUMNS` explicitly). Its owner publishes the TXT record `_<app id>-domain-verification.<host>` = `<app id>-domain-verification=<token>`, where `<app id>` is the deployment's own `SCHEMAVAULTS_AUTH_SERVER_APP_ID` (`getDomainVerificationRecordPrefix()`: e.g. `_schemavaults-auth-domain-verification.api.example.com`, `_acme-auth-domain-verification.…`; an app id longer than 42 characters is shortened to keep the record name one DNS label; changing a deployment's app id renames its records, so owners re-publish them; `getDnsVerifiableHostname()` / `buildDomainVerificationTxtRecord()`; ports and paths don't matter) and calls `POST /api/apis/{api_server_id}/domains/{api_server_domain_ref_id}/verify` (managers; `API_SERVER_DOMAIN_VERIFICATION_RATE_LIMIT`, ip+uid): 200 verified, 422 `verification_record_not_found` / `domain_not_dns_verifiable` (loopback, IP-literal, single-label and `.localhost` hosts: `dns_txt_record` is null), 503 `dns_lookup_failed` (no authoritative answer: nothing changes). `{ "method": "administrator" }` lets a platform administrator attest any domain. `lookupTxtRecords()` (node `Resolver`, injectable for tests) answers `.invalid` names as nonexistent without a query (RFC 6761 §6.4), which is what the E2E specs use. Every authoritative answer is also a re-check (`planDnsVerification()`): DNS-verified registrations of the same host (any API server, any environment, the checked one included) whose record is gone return to pending, so a domain's new owner takes it over from a previous owner's stale verification; administrator attestations are never revoked by DNS. Migration 00057 backfilled tokens and attested the existing rows of platform-owned API servers (`administrator`); every other existing row starts pending. The verification state is the wire `ApiServerDomainVerification` (`@schemavaults/app-definitions`): `verifications` beside `list` on `GET /api/apis/{api_server_id}/domains` (empty for hardcoded API servers), `verification` on the add-domain response, the client SDK's `listApiServerDomainVerifications()` / `verifyApiServerDomain()` (unverified outcomes resolve with `verified: false` + `error`), and a Verified / Unverified `ApiServerDomainVerificationBadge` (`@schemavaults/auth-ui`; `data-testid="api-server-domain-{verified|unverified}-<ref id>"`) next to each domain, both on `/apis/[api_server_id]` (with the `VerifyApiServerDomainDialog` of `auth-server/src/components/ApiServerDomainVerification/`) and in the API servers table (`ApiServerDomainsList`: SSR-preloaded `domain_verifications` from `preloadApiServersTable()`, refreshed by `useApiServerDomainVerifications()`, whose SWR key the add / remove domain dialogs invalidate through `isApiServerDomainsCacheKey()`). The E2E seed route attests the example resource server's domain. Pinned by `apis/ApiServerDomainVerification.cy.ts` and `dynamic_client_registration/ResourceUrlDomainSquatting.cy.ts` (which toggles `require_api_server_domain_verification` and restores it to off).

Policy management: `PATCH /api/apis/[api_server_id]` (`allow_dynamic_clients`, `resource_url_match_mode`; `canUserManageResource`), `SchemaVaultsApiServerRegistry.setApiServerDynamicClientPolicy()`, the client SDK's `updateApiServerDynamicClientPolicy()`, and `<ApiServerDynamicClientsCard />` on `/apis/[api_server_id]`. The E2E seed route accepts `allow_dynamic_clients` / `resource_url_match_mode`.

Resource servers built on `@schemavaults/auth-server-sdk` must opt into URL audiences: `RouteGuardFactory({ accepted_audiences: [url] })`, `SchemaVaultsServerMiddleware({ accepted_audiences })`, or `decodeJWTsWithKeyManager(…, { accepted_audiences })`. `resolveExpectedTokenAudience()` reads the presented token's unverified header `aud`; if it is one of the accepted URLs that value is enforced by the decode, otherwise the API server id form is (keysets are always looked up by the id). `createSchemaVaultsAuthResolvers()` (the `/openapi-operations` sub-export) always accepts `SCHEMAVAULTS_RESOURCE_URL` (and its trailing-slash twin, `resourceUrlAudiences()`) on top of its `acceptedAudiences`. That env var is also the `resource` of the RFC 9728 protected resource metadata a resource server publishes with `createOAuthProtectedResourceMetadataRoute()` (`@schemavaults/auth-server-sdk/oauth-protected-resource`, mounted at `app/.well-known/oauth-protected-resource/[[...path]]/route.ts`; `authorization_servers` = the auth server URL, `bearer_methods_supported: ["header"]`, CORS `*`, 404 when the env var is unset or for a path-suffixed request about another resource), which is how MCP clients discover the auth server and the `resource` to request. The example resource server publishes it (`src/app/.well-known/oauth-protected-resource/`) and additionally reads `SCHEMAVAULTS_ACCEPTED_TOKEN_AUDIENCES` (comma-separated) in `auth-resolvers.ts`.

## Client SDK & tests

`@schemavaults/auth-client-sdk`: `registerDynamicClient(metadata)` on the client (and the standalone `registerDynamicClient({ adapter, auth_server_uri, metadata })`), throwing `DynamicClientRegistrationFailedError` (`status`, `error`, `error_description`, `isRfc7591Error()`) on refusal; `updateApiServerDynamicClientPolicy(api_server_id, update)`.

E2E: the standalone `dynamic_client_registration` suite (`tests/e2e-auth-tests/cypress/e2e/dynamic_client_registration/`) runs with the example resource server (`suiteNeedsExampleResourceServer()` in `e2e-auth-tests-cli.ts` selects the `e2e_with_resource_server` compose profile and generates JWKS keys; `cypress.config.ts` seeds the example app/API with `allow_dynamic_clients: true, resource_url_match_mode: "prefix"`; docker-compose sets the resource server's `SCHEMAVAULTS_RESOURCE_URL` to `http://example-nextjs-resource-server/api`, and the suite checks the protected resource metadata it publishes) and has its own job in `run-e2e-tests.yml`. It toggles the setting through `PATCH /api/admin/settings/allow_dynamic_client_registration` as the superuser and restores it afterwards.
