# Client Credentials Grant & Service Accounts

`grant_type=client_credentials` (RFC 6749 §4.4) is the third grant at `POST /api/oidc/token` (advertised in `grant_types_supported` by `buildOidcProviderMetadata()` in `@schemavaults/auth-common`). It is restricted to **confidential clients**: `authenticateTokenEndpointClient` runs first as for every grant, and `handleOidcClientCredentialsGrant` (`auth-server/src/app/api/oidc/token/client_credentials_grant.ts`) refuses a client that did not authenticate with its secret (`OidcGrantContext.client_authenticated === false`, i.e. a public or hardcoded app) with a 400 `unauthorized_client`. Per-IP rate limit: `CLIENT_CREDENTIALS_RATE_LIMIT` (own bucket, separate from refresh grants).

There is no resource owner, so tokens are minted for the app's **service account**: a `USERS` row with `service_account_app_id = <app_id>` (migration 00038; one per app via a partial unique index; `ON DELETE CASCADE` from `APPS`), a synthetic email `<app_id>@<domain>` (`serviceAccountEmailForApp`), `email_verified = true`, and **no `PASSWORDS` row**. The domain is the `service_account_email_domain` server setting (`auth-server/src/lib/config/service-account-email-domain.ts`; admin-editable at `/admin/settings`, validated by `serviceAccountEmailDomainSchema` as a bare hostname), defaulting to `DEFAULT_SERVICE_ACCOUNT_EMAIL_DOMAIN = service-accounts.invalid` — an RFC 2606/6761 reserved TLD that never resolves and can never receive mail; operators may instead set a domain they own (e.g. `service-accounts.auth.example.com`). Both the configured domain and the built-in default are **reserved**: `isReservedServiceAccountEmail` + `getReservedServiceAccountEmailDomains` refuse human registration under them with a 400 (`RESERVED_EMAIL_DOMAIN_MESSAGE`) in `handle_register.ts`, and `createUser` throws `ReservedEmailDomainError` as the last line of defense for every account-creation path. It is created lazily by the first grant — `getOrCreateAppServiceAccount` in `auth-server/src/lib/auth-db/apps/app-registry/app-service-accounts.ts` inserts the user plus its `authorized_apps` row in one transaction, so the shared `validateAudience`/`isAppAuthorizedForUser` checks hold by construction — or explicitly via the management API. `loadUserData` maps the column to `UserData.service_account: true`, `generateJWT` copies that into the encrypted token payload (`CustomJWTPayload.service_account`, optional) and `customJwtPayloadToUserData` carries it back out, so resource servers using the server SDK's route guards can tell an M2M caller from a person (`user.service_account === true`).

Grant semantics: `scope` is optional; unknown scopes AND `openid` are dropped (no end user was authenticated, so no id_token is ever issued) and the granted set is echoed back per §5.1; a malformed value is `invalid_scope`. The RFC 8707 `resource` parameter selects the audience exactly like the other grants (default: the reserved `oidc-userinfo` audience, which keeps the token introspectable by the client at `/api/oidc/introspect` — `/api/oidc/userinfo` still refuses it with `insufficient_scope`, as for any token without `openid`; a token for an API server is introspectable by that API server instead (`private_key_jwt`, see the `oidc-confidential-clients` skill); an API server id requires the app to be connected to it, else `invalid_target`; the auth server's own audience is never available). The response is the access token only — `issueOidcTokens({ issue_refresh_token: false })` yields `IssuedOidcTokens.refresh_token === null`, so no `refresh_token`/`refresh_token_expires_in` and `deliverOidcTokens` always answers inline. Issued-token tracking records `grant_type: "client_credentials"` (`IssuedTokenGrantType`). A disabled service account (admin action on the user) is refused with `unauthorized_client`.

Service accounts must never behave like human accounts: `handle_login.ts` answers a service-account email exactly like an unknown email (constant-time dummy verification, 401) and `handle_reset_password_request.ts` swallows reset requests for them. Management: `GET`/`POST`/`DELETE /api/apps/[app_id]/service-account` (guarded by `loadAppForManagement`; `POST` is idempotent, `DELETE` goes through `deleteUser` so the uid is tombstoned and the next grant creates a fresh identity), `SchemaVaultsAppRegistry.getServiceAccount/getOrCreateServiceAccount/deleteServiceAccount`, client SDK `getClientApplicationServiceAccount`/`createClientApplicationServiceAccount`/`deleteClientApplicationServiceAccount`, and the `AppServiceAccountCard` on the app detail page (`auth-server/src/components/AppOAuthSecurity/`). E2E: `tests/e2e-auth-tests/cypress/e2e/example_resource_server/ClientCredentialsGrant.cy.ts` (the confidential seed app is connected to the example resource server's API through the seed route's `connect_to_api_server_ids` option so the spec can exercise a real resource-server call), the discovery/validation assertions in the `misc` suite, `register/ServiceAccountEmailDomain.cy.ts` (nobody can register under the default domain) and `admin/ServiceAccountEmailDomainSetting.cy.ts` (setting validation; a configured domain AND the default stay unregistrable).

## Organization membership of a service account

Service accounts cannot accept invitations and `POST /api/organizations/[organization_id]/members` refuses them, so resource servers whose route guards require organization membership (the server SDK's `required_organization` / `organization` options, which ask `GET /api/resource-server/organizations/[organization_id]/members/[uid]/role` through `isUserInOrganization()`) would otherwise always refuse M2M tokens. The managers of an **organization-owned** app (`loadAppForManagement`) opt its service account into the owning organization instead: `PUT /api/apps/[app_id]/service-account/organization-membership` (`{ role: "member" | "owner" }`, default `member`; 409 for platform-owned, user-owned and dynamically registered apps, and for apps without a service account yet) and `DELETE` (404 when not a member). The setting is a row of `APP_SERVICE_ACCOUNT_ORGANIZATION_ROLES` (migration 00043; one per app, `ON DELETE CASCADE` from `APPS`; `app-service-account-organization-roles.ts`), keyed by the app but only ever stored alongside its service account: `PUT` refuses an app with no service account, removing the service account (the management `DELETE` or an admin deleting its user, both through `deleteUser()`, which clears the row in the same transaction) clears it, and `getOrCreateAppServiceAccount` clears any stale row when it creates one, so a new or recreated service account always starts outside the organization. The organization is **not** stored: `listUserOrganizationMemberships` adds a **virtual** membership (`membership_declaration_id` `service-account-virtual-<app_id>`, like the platform admins' `admin-virtual-<uid>` one; `getVirtualOrganizationMembershipSource()` tells them apart) via `getServiceAccountVirtualOrganizationMembership(db, uid)`, a single join `USERS → APPS → APP_SERVICE_ACCOUNT_ORGANIZATION_ROLES` restricted to `owner_type = 'organization'`, so the membership always names the app's current owner and never counts against `MAXIMUM_USER_ORGANIZATIONS`. Every membership check built on that function sees it (the resource-server role endpoint, the auth server's `isUserInOrganization`, the admin user page's Organizations card, which badges it "Virtual"); the organization's own member list (`listOrganizationMembers`) does not show it. `GET /api/apps/[app_id]/service-account` reports `organization_membership: { available, organization_id, role }` (`summarizeServiceAccountOrganizationMembership()` in `auth-server/src/lib/ownership/service-account-organization-membership.ts`); the client SDK has `setClientApplicationServiceAccountOrganizationMembership(app_id, role?)` / `deleteClientApplicationServiceAccountOrganizationMembership(app_id)`; `AppServiceAccountCard` shows an "Organization membership" role select for organization-owned apps once the service account exists (its remove dialog says the membership goes too), and only sends the change when the user clicks its Save button. The resource-server role endpoint converts the looked-up user document with `userDocumentToUserData()` (spreading it used to fail the strict `userDataSchema` on `service_account_app_id` and answer 500 for any service-account uid). E2E: `resource_management/ServiceAccountOrganizationMembership.cy.ts` (including the card: hidden without a service account, nothing sent before Save; the role is cleared by both deletion paths; `PUT` without a service account is a 409), plus the 409 / response-shape assertions in `api_contract/AppServiceAccountApiLifecycle.cy.ts`.
