# Client Credentials Grant & Service Accounts

`grant_type=client_credentials` (RFC 6749 §4.4) is the third grant at `POST /api/oidc/token` (advertised in `grant_types_supported` by `buildOidcProviderMetadata()` in `@schemavaults/auth-common`). It is restricted to **confidential clients**: `authenticateTokenEndpointClient` runs first as for every grant, and `handleOidcClientCredentialsGrant` (`auth-server/src/app/api/oidc/token/client_credentials_grant.ts`) refuses a client that did not authenticate with its secret (`OidcGrantContext.client_authenticated === false`, i.e. a public or hardcoded app) with a 400 `unauthorized_client`. Per-IP rate limit: `CLIENT_CREDENTIALS_RATE_LIMIT` (own bucket, separate from refresh grants).

There is no resource owner, so tokens are minted for the app's **service account**: a `USERS` row with `service_account_app_id = <app_id>` (migration 00038; one per app via a partial unique index; `ON DELETE CASCADE` from `APPS`), a synthetic email `<app_id>@<domain>` (`serviceAccountEmailForApp`), `email_verified = true`, and **no `PASSWORDS` row**. The domain is the `service_account_email_domain` server setting (`auth-server/src/lib/config/service-account-email-domain.ts`; admin-editable at `/admin/settings`, validated by `serviceAccountEmailDomainSchema` as a bare hostname), defaulting to `DEFAULT_SERVICE_ACCOUNT_EMAIL_DOMAIN = service-accounts.invalid` — an RFC 2606/6761 reserved TLD that never resolves and can never receive mail; operators may instead set a domain they own (e.g. `service-accounts.auth.example.com`). Both the configured domain and the built-in default are **reserved**: `isReservedServiceAccountEmail` + `getReservedServiceAccountEmailDomains` refuse human registration under them with a 400 (`RESERVED_EMAIL_DOMAIN_MESSAGE`) in `handle_register.ts`, and `createUser` throws `ReservedEmailDomainError` as the last line of defense for every account-creation path. It is created lazily by the first grant — `getOrCreateAppServiceAccount` in `auth-server/src/lib/auth-db/apps/app-registry/app-service-accounts.ts` inserts the user plus its `authorized_apps` row in one transaction, so the shared `validateAudience`/`isAppAuthorizedForUser` checks hold by construction — or explicitly via the management API. `loadUserData` maps the column to `UserData.service_account: true`, `generateJWT` copies that into the encrypted token payload (`CustomJWTPayload.service_account`, optional) and `customJwtPayloadToUserData` carries it back out, so resource servers using the server SDK's route guards can tell an M2M caller from a person (`user.service_account === true`).

Grant semantics: `scope` is optional; unknown scopes AND `openid` are dropped (no end user was authenticated, so no id_token is ever issued) and the granted set is echoed back per §5.1; a malformed value is `invalid_scope`. The RFC 8707 `resource` parameter selects the audience exactly like the other grants (default: the reserved `oidc-userinfo` audience, which keeps the token introspectable at `/api/oidc/introspect` — `/api/oidc/userinfo` still refuses it with `insufficient_scope`, as for any token without `openid`; an API server id requires the app to be connected to it, else `invalid_target`; the auth server's own audience is never available). The response is the access token only — `issueOidcTokens({ issue_refresh_token: false })` yields `IssuedOidcTokens.refresh_token === null`, so no `refresh_token`/`refresh_token_expires_in` and `deliverOidcTokens` always answers inline. Issued-token tracking records `grant_type: "client_credentials"` (`IssuedTokenGrantType`). A disabled service account (admin action on the user) is refused with `unauthorized_client`.

Service accounts must never behave like human accounts: `handle_login.ts` answers a service-account email exactly like an unknown email (constant-time dummy verification, 401) and `handle_reset_password_request.ts` swallows reset requests for them. Management: `GET`/`POST`/`DELETE /api/apps/[app_id]/service-account` (guarded by `loadAppForManagement`; `POST` is idempotent, `DELETE` goes through `deleteUser` so the uid is tombstoned and the next grant creates a fresh identity), `SchemaVaultsAppRegistry.getServiceAccount/getOrCreateServiceAccount/deleteServiceAccount`, client SDK `getClientApplicationServiceAccount`/`createClientApplicationServiceAccount`/`deleteClientApplicationServiceAccount`, and the `AppServiceAccountCard` on the app detail page (`auth-server/src/components/AppOAuthSecurity/`). E2E: `tests/e2e-auth-tests/cypress/e2e/example_resource_server/ClientCredentialsGrant.cy.ts` (the confidential seed app is connected to the example resource server's API through the seed route's `connect_to_api_server_ids` option so the spec can exercise a real resource-server call), the discovery/validation assertions in the `misc` suite, `register/ServiceAccountEmailDomain.cy.ts` (nobody can register under the default domain) and `admin/ServiceAccountEmailDomainSetting.cy.ts` (setting validation; a configured domain AND the default stay unregistrable).
