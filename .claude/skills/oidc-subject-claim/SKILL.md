# OIDC Subject Claim Format

The OIDC-facing `sub` claim is namespaced by the deployment's own app id, Auth0-style: `<auth_server_app_id>|<uid>` (e.g. `schemavaults-auth|4f7c…`), built/parsed by `formatOidcSubClaim`/`parseOidcSubClaim` in `@schemavaults/auth-common` (`src/oidc/sub-claim.ts`; the `|` delimiter can never appear in an app id). The id_token (`generateIdToken` in `@schemavaults/jwt`, prefix from the optional `auth_server_app_id` option defaulting to `getAuthServerAppId()`), `GET/POST /api/oidc/userinfo` and RFC 7662 introspection (which also reports the bare `uid` alongside) must agree on it exactly (OIDC Core §5.3.2). Because `SCHEMAVAULTS_AUTH_SERVER_APP_ID` is stable per deployment, subjects are stable per user; changing that env var changes every subject, so RPs keying storage on `sub` see new identities.

## `UserData.sub`

`UserData.sub` (`@schemavaults/auth-common` `user_data/user_data.ts`) is the same OIDC form; `uid` is the platform user id, and everything keyed on a user (DB lookups, org roles, revocation) uses `uid`. Before the switch `sub` duplicated the bare uid, and bare uuids still arrive from older auth servers' JSON, from browser caches (the react provider's `user_data` localStorage entry) and from token payloads, so parsing upgrades them lazily: `userDataSchema` preprocesses a bare-uuid `sub` into `<app_id>|<uuid>` before validating, and its refine requires the subject to name the `uid`. The prefix comes from `createUserDataSchema({ auth_server_app_id })` (an app id or a function), or, for the default `userDataSchema`, from `getAuthServerAppId()` at parse time (runtimes without `process.env` fall back to `DEFAULT_AUTH_SERVER_APP_ID`). Browser code must therefore pass its configured app id: the client SDK's whoami parse (`checkIfAuthenticatedWithServer`), the react adapter's user-data cache (`ReactAuthClientSdkAdapter`, which also stores the parsed, upgraded value) and auth-ui's `useAllUsersList` (`useAuthServerAppId()`) do. Helpers: `toUserDataSubClaim`, `uidFromUserDataSubClaim`, `isUserDataSubClaim`. Server code that builds UserData from a user row uses `formatOidcSubClaim(getAuthServerAppId(), uid)` (`loadUserData`, the admin users page, the resource-server org-role operation). A subject that is already in OIDC form is never re-prefixed, whatever its app id (`iss` pins the deployment).

## Tokens keep the bare uid

The platform's encrypted access/refresh token payloads are not UserData: they keep `sub === uid` on the wire (`payload_data.ts`, `signJWT`'s inner signature), because published `@schemavaults/auth-server-sdk` / `@schemavaults/jwt` versions on resource servers reject any other `sub`. `customJwtPayloadToUserData(payload, auth_server_app_id = getAuthServerAppId())` builds the OIDC `sub` from the uid when a decoded token becomes UserData, and `decodeJWTs`' cross-token consistency check accepts either form (`uidFromUserDataSubClaim(user.sub) === user.uid`). JSON responses carrying UserData (whoami, login/register `userData`) emit the OIDC form, so apps on client SDKs older than this change (whose `userDataSchema` required a bare-uuid `sub`) must upgrade to read them.
