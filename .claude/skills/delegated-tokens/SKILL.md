# Delegated tokens (RFC 8693 actor claim)

**What one is.** An access token whose `sub` is still the user (with the user's granted scope) and whose `act` claim names the CURRENT actor — who is actually calling on the user's behalf, e.g. a client app's agent — with prior actors of a delegation chain nested (`act.act`, at most `MAX_JWT_ACTOR_CLAIM_DEPTH` = 3 levels). RFC 8693 §4.1: access control may use only the top-level claims and the current actor; prior actors are informational. Only identity claims sit in `act`: `sub` (the actor's bare uid on the wire, like the token's own `sub`) and optionally `client_id` (the app it acts through).

**Token format** (`@schemavaults/jwt` 0.16.0, `src/jwt/actor-claim.ts`): `act` is an optional ACCESS-token claim of the strict payload schema (`createJwtActorClaimSchema`: strict objects built level by level, no `z.lazy`); `generateJWT` / `JWT_Factory.access(aud, { actor })` embed it and refuse it on refresh tokens; `getActorFromCustomJwtPayload()` returns a `TokenActor` (`uid`, OIDC-form `sub` `<auth_server_app_id>|<uid>`, `client_id`, `prior_actor`); `customJwtPayloadToUserData()` never copies it into `UserData`. The inner `sig` does not cover it (the JWE does). Since 0.17.0 an access token can also expire early: `generateJWT({ expires_at })` / `JWT_Factory.access(aud, { expires_at })` (unix ms, floored to seconds, capped at the default lifetime, refused on refresh tokens: `token-lifetime.ts`), and `decodeJWT()` returns the token's `exp` (unix seconds) instead of stripping it. Every decoder version refuses a token past its `exp` (jose), so a shorter lifetime needs no opt-in. Decoders before 0.16.0 reject any token carrying `act`, which is why emission is gated per API server (below).

**What resource servers see** (`@schemavaults/auth-server-sdk` ≥ 0.39.0): `decodeJWTsWithKeyManager()` returns `actor` next to `client_app_id`; route guards expose `guard.actor` (null without `act`, when no user resolved, or when revoked); `createSchemaVaultsAuthResolvers()` puts `actor` (`{ sub, clientId?, actor? }`, `AuthPrincipalActor` in `@schemavaults/openapi-operations`) on the principal; ≥ 0.40.0 types introspection's `act` and `service_account` (`tokenIntrospectionResultSchema`; a malformed `act` throws rather than being dropped) and maps the actor with `getActorFromIntrospectionResult()` to the same `TokenActor`. The auth server's `POST /api/oidc/introspect` reports `act` via `toOidcIntrospectionActor()` (`auth-server/src/lib/oidc/introspection/introspection-actor.ts`: OIDC `sub` plus `uid`, `client_id`, prior actors nested). Operations of `@schemavaults/openapi-operations` ≥ 0.7.0 declare who may call them with `requireAuth({ delegatedCallers })` (`DelegatedCallerPolicy`, `auth-scheme.ts`): `"allowed"` (default) or `"refused"`, which `resolveAuth()` answers with 403 `delegated_caller_refused` for any principal with an `actor` (`isDelegatedPrincipal()`), first among the authorization checks (before the route guard, scopes and organization role; no admin bypass). The `x-schemavaults-auth` extension carries `delegatedCallers` only when the operation sets it (existing documents are unchanged), `documentRuntimeResponses` adds the reason to the 403, and `@schemavaults/openapi-docs-ui` shows a "no delegated callers" badge and a "Delegated callers" row. The example resource server's `POST /api/me/account-deletion` refuses them. Finer rules (e.g. one client's agents only) stay in handlers via `ctx.auth.actor`; route guards (`RouteGuardFactory`) have no declarative policy, handlers there check `guard.actor`.

**The opt-in** (`accept_delegated_tokens`, migration `00052-api-server-delegated-tokens.ts`: `API_SERVERS.accept_delegated_tokens BOOLEAN NOT NULL DEFAULT false`). `@schemavaults/app-definitions` `api-server-delegated-tokens.ts`: the optional definition field (`apiServerDelegatedTokenFieldsShape`, absent = false) and `doesApiServerAcceptDelegatedTokens(api_server)` — true only for a non-hardcoded definition with the flag set, so the auth server's own API and the `oidc-userinfo` audience never accept delegated tokens (nobody may act for a user against the user's own account), and neither does an unknown API server. Set by `PUT /api/apis/{api_server_id}/delegated-token-policy` (`{ accept_delegated_tokens: boolean }`, strict; the API server's managers per `canUserManageResource` — org owners/admins, the owning user — or platform admins; hardcoded → 403; registry `setApiServerDelegatedTokenPolicy()`); creation refuses `accept_delegated_tokens: true` with 400 (`create.operation.ts`), so the PUT is the only way in. Client SDK: `setApiServerDelegatedTokenPolicy(api_server_id, accept)` (auth-server app only, like the other management writes). UI: `ApiServerDelegatedTokensCard` (`auth-server/src/components/ApiServerDelegatedTokens/`, `data-testid` `api-server-delegated-tokens-card` / `accept-delegated-tokens-switch`) on `/apis/[api_server_id]` for non-hardcoded servers. Managers turn it on once their resource server runs auth-server-sdk ≥ 0.39.0 (jwt ≥ 0.16.0).

**Issuance gate.** `issueOidcTokens({ actor })` (`auth-server/src/lib/oidc/issue-oidc-tokens.ts`) calls `assertDelegatedTokenIssuance()` (`delegated-token-issuance.ts`, unit-tested with an injected loader) before minting anything: the access token must come ALONE — `issue_refresh_token: false` and no id_token (TypeError otherwise: a refresh token cannot carry `act`, so refreshing it would mint plain user tokens and launder the delegation away) — and the access token's API server (`access_token_audience_api_server_id`, or the audience mapped by `getApiServerIdForTokenAudience`) must pass `doesApiServerAcceptDelegatedTokens()`, else `DelegatedTokensNotAcceptedError` (`@/lib/error/`), which a grant answers with `invalid_target` (RFC 8693 §2.2.2). The actor then flows through `generateTokensForAuthenticatedUser({ actor })` and `generateAccessToken({ actor })` into `JWT_Factory.access()`; never call those two with an actor directly.

**The emitter: RFC 8693 token exchange** (`auth-server/src/app/api/oidc/token/token_exchange_grant.ts`, steps in `auth-server/src/lib/oidc/token-exchange/`). `grant_type=urn:ietf:params:oauth:grant-type:token-exchange` (`TOKEN_EXCHANGE_GRANT_TYPE`) at `POST /api/oidc/token`, for confidential clients only (they authenticated with their secret; never dynamically registered ones — `isGrantTypeAllowedForClientApp` refuses them like client_credentials), with its own per-IP `TOKEN_EXCHANGE_RATE_LIMIT`. The client presents `subject_token` = an access token one of its users holds for an API server (`subject_token_type=urn:ietf:params:oauth:token-type:access_token`, the only type; `requested_token_type` may only name it too; `actor_token` → `invalid_request`, `audience` → `invalid_target`: `parse-token-exchange-request.ts`, pure). The other grants refuse the RFC 8693 parameters (`subject_token`, `subject_token_type`, `requested_token_type`, `actor_token`, `actor_token_type`) and a token exchange refuses the other grants' own (`code`, `code_verifier`, `redirect_uri`, `refresh_token`, `refresh_token_delivery`), both with `invalid_request` before doing anything (`findMisplacedTokenExchangeParam()` in `token-request.ts`, pure; `audience` is left out because many OAuth libraries send it with every grant; the shared `client_id`, `client_secret`, `scope` and `resource` stay allowed everywhere). `verifyTokenExchangeSubjectToken()` verifies it exactly as that API server's introspection would (`decodeIntrospectableToken` + `isIntrospectedTokenActive` with an `api_server` caller: keyset, expiry, revoked `jti`, `tokens_valid_after`, the user's consent, the app-to-API connection) and requires `app` = the client, no `act` (no re-delegation, no renewing a delegated token by exchanging it), no `service_account`; the auth server's own and the `oidc-userinfo` audiences never qualify. Every subject-token failure is `invalid_request` (RFC 8693 §2.2.2). The delegated token never holds more than its subject token: same user, client and audience (`resource` is optional and must equal the subject token's `aud`, else `invalid_target`; to act at another API server, exchange a token for that one — the refresh grant mints it with `resource`), and `resolveTokenExchangeScope()` (pure) narrows the subject's scope like the refresh grant (`narrowGrantedScope`; wider → `invalid_scope`), then drops API scopes no longer usable (`listUsableApiScopeValues`: withdrawn consent, removed allowance). It never outlives the subject token either: `resolveDelegatedTokenExpiry()` (pure) sets its expiry to the subject token's `exp` (`issueOidcTokens({ access_token_expires_at })`, so `expires_in` and introspection's `exp` report the shortened lifetime), and a subject token with under `MIN_DELEGATED_TOKEN_LIFETIME_SECONDS` (30) left is `invalid_request`: the client renews the user's token and exchanges the new one. It joins the subject token's session: `verifyTokenExchangeSubjectToken()` looks up the subject's `ISSUED_TOKENS.refresh_jti` (`getAccessTokenSessionRefreshJti()`) and `issueOidcTokens({ session_refresh_jti })` records the delegated token with it (refused alongside a freshly minted refresh token). The actor is the client's service account (`getOrCreateServiceAccount`; disabled → `unauthorized_client`): `act = { sub: <service account uid>, client_id }`. `issueOidcTokens({ actor, issue_refresh_token: false, include_id_token: false, grant_type: "token_exchange" })` enforces the opt-in (`DelegatedTokensNotAcceptedError` → `invalid_target`); the response adds `issued_token_type` (§2.2.1). `token_exchange` is in `ISSUED_TOKEN_GRANT_TYPES` (`issued-tokens-table.ts`: the ISSUED_TOKENS rows, `recordIssuedTokens` validation and the admin token listing schema share it). The grant type and token type URNs are `OAUTH_TOKEN_EXCHANGE_GRANT_TYPE` / `OAUTH_ACCESS_TOKEN_TYPE` in `@schemavaults/auth-common` (`oidc/token-exchange.ts`; the auth server's `token-exchange-constants.ts` re-exports them as `TOKEN_EXCHANGE_GRANT_TYPE` / `ACCESS_TOKEN_TYPE`), and discovery lists the grant in `grant_types_supported` (`buildOidcProviderMetadata()`).

**Calling it from a confidential backend** (`@schemavaults/auth-server-sdk` ≥ 0.41.0, sub-export `/confidential-client`, also on the root barrel): `exchangeTokenForDelegatedToken({ auth_server_url, client_id, client_secret, subject_token, scope?, resource? })` posts the exchange with `client_secret_basic` (URL-encoded id and secret, as `parseBasicClientCredentials` decodes them; never `client_secret` in the body), takes `scope` as a string or list (empty → TypeError: omit it to keep the subject's scope) and validates the response (`delegatedTokenResponseSchema`: `issued_token_type` must be the access-token URN). `revokeToken({ ..., token, token_type_hint? })` posts to `/api/oidc/revoke` the same way. Both throw `OAuthEndpointError` (`status`, `error`, `error_description`; `error` null for a non-JSON refusal) so callers branch on `invalid_target` (API server does not accept delegated tokens), `invalid_request` (subject token unusable), `invalid_scope`. There is no `auth-client-sdk` wrapper: that SDK is browser-facing and the exchange needs the client secret.

**Ending a delegated token.** The client revokes it at `POST /api/oidc/revoke` (RFC 7009): `decodeRevocableToken()` verifies an API-server-audience access token that carries `act` with its API server's keyset (`decodeApiServerAccessToken`) and revokes its `jti` (other API-server access tokens still answer `unsupported_token_type`). Introspection and resource servers with an `isTokenRevoked` hook then refuse it; resource servers verifying locally only stop accepting it at expiry. It also dies with the user's consent to the app (app de-authorization, introspection's consent check) and `tokens_valid_after`. It is recorded in the session its subject token was issued in (`refresh_jti` = the subject token's), so logout and RFC 7009 revocation of that refresh token revoke it with the session's own access tokens (`revokeTokensIssuedWithRefreshToken`). As for any access token, a subject token minted with an earlier refresh token of a rotation chain is linked to that one, not the current one; the delegated token still dies with the subject token's expiry.

**The worked example** (`tests/example-nextjs-resource-server`, `/agents`; E2E suite `agents`, CI job `Run-Agents-E2E-Tests`). A third-party app's whole loop: `src/lib/agents/auth/agents-sign-in.ts` signs the user in as the confidential client (openid-client; `resource` = the example API, scope `AGENTS_SIGN_IN_SCOPE`: `openid email example:notes.read`, consented per scope) and keeps the tokens server-side (in memory, `runtime/state.ts`); each agent session (`runtime/agent-sessions.ts`) gets a delegated token from `exchangeTokenForDelegatedToken()` narrowed with `delegatedScopeFor()` (`openid` + the scopes picked on the new-session screen) and a sandbox (`sandbox/agent-sandbox.ts`: `@schemavaults/sandbox-management-sdk` from npm, with the example's `LocalProcessSandboxProvider`: child processes in a per-sandbox directory, scrubbed env, refused in production/staging, no `spec.network`/`spec.start`). The token goes in a file (`.agent/access-token`, rewritten on renewal), not `spec.env`. A deterministic fake model (`model/fake-agent-model.ts`) maps prompts to fixed tool commands (`node agent-tools/api.mjs GET /api/whoami`, notes, email, account deletion, `env`, `ls`) and explains the API's answers. "Revoke access" / "End session" call `revokeToken()` (end also destroys the sandbox), "Grant access again" exchanges anew; sign-out revokes the user's refresh token only, and the session linkage revokes the agents' tokens with it. The example API wraps `createSchemaVaultsAuthResolvers()` in `withDelegatedTokenIntrospection()` (`src/lib/api/delegated-token-introspection.ts`): principals with an `actor` are introspected as the API server on every request (inactive → 401 `token_revoked`, auth server unreachable → 503), the user's own tokens stay local-only. The UI is `@schemavaults/ui`'s `AgentSessions` (`src/app/agents/agent-workspace.tsx`, Server Functions in `actions.ts`). The spec signs fresh users in through the real login and consent pages and checks the actor and scope the API sees, scope narrowing (403 `insufficient_scope`), `delegated_caller_refused`, no app secrets in the sandbox, revoke / grant again, end session, and sign-out cutting the agent off.

**Not there yet.** The server SDK's `isTokenRevoked` hook (`DecodedTokenClaims`) gets neither the raw token nor the actor, so a resource server cannot introspect delegated tokens through it; the example's `withDelegatedTokenIntrospection()` is the pattern a `createSchemaVaultsAuthResolvers()` option could ship. A client cannot ask for a delegated token shorter than what its subject token has left (e.g. minutes for a sandboxed agent whose env is persisted): the plumbing exists (`access_token_expires_at` on `issueOidcTokens()`, introspection reports the real `exp`), a request parameter (refused on the other grants like the RFC 8693 ones) does not. Every agent of an app shares one actor (its service account), so an API server cannot tell one agent session from another. A server-side delegation record (agent sessions the user can see and end on `/account/connected-apps`, re-exchange gated on it) does not exist yet.
