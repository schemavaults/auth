# Delegated tokens (RFC 8693 actor claim)

**What one is.** An access token whose `sub` is still the user (with the user's granted scope) and whose `act` claim names the CURRENT actor — who is actually calling on the user's behalf, e.g. a client app's agent — with prior actors of a delegation chain nested (`act.act`, at most `MAX_JWT_ACTOR_CLAIM_DEPTH` = 3 levels). RFC 8693 §4.1: access control may use only the top-level claims and the current actor; prior actors are informational. Only identity claims sit in `act`: `sub` (the actor's bare uid on the wire, like the token's own `sub`) and optionally `client_id` (the app it acts through).

**Token format** (`@schemavaults/jwt` 0.16.0, `src/jwt/actor-claim.ts`): `act` is an optional ACCESS-token claim of the strict payload schema (`createJwtActorClaimSchema`: strict objects built level by level, no `z.lazy`); `generateJWT` / `JWT_Factory.access(aud, { actor })` embed it and refuse it on refresh tokens; `getActorFromCustomJwtPayload()` returns a `TokenActor` (`uid`, OIDC-form `sub` `<auth_server_app_id>|<uid>`, `client_id`, `prior_actor`); `customJwtPayloadToUserData()` never copies it into `UserData`. The inner `sig` does not cover it (the JWE does). Decoders before 0.16.0 reject any token carrying `act`, which is why emission is gated per API server (below).

**What resource servers see** (`@schemavaults/auth-server-sdk` ≥ 0.39.0): `decodeJWTsWithKeyManager()` returns `actor` next to `client_app_id`; route guards expose `guard.actor` (null without `act`, when no user resolved, or when revoked); `createSchemaVaultsAuthResolvers()` puts `actor` (`{ sub, clientId?, actor? }`, `AuthPrincipalActor` in `@schemavaults/openapi-operations`) on the principal; ≥ 0.40.0 types introspection's `act` and `service_account` (`tokenIntrospectionResultSchema`; a malformed `act` throws rather than being dropped) and maps the actor with `getActorFromIntrospectionResult()` to the same `TokenActor`. The auth server's `POST /api/oidc/introspect` reports `act` via `toOidcIntrospectionActor()` (`auth-server/src/lib/oidc/introspection/introspection-actor.ts`: OIDC `sub` plus `uid`, `client_id`, prior actors nested). Operations decide what an actor may do (the SDK README shows refusing principals with an actor on a sensitive operation).

**The opt-in** (`accept_delegated_tokens`, migration `00052-api-server-delegated-tokens.ts`: `API_SERVERS.accept_delegated_tokens BOOLEAN NOT NULL DEFAULT false`). `@schemavaults/app-definitions` `api-server-delegated-tokens.ts`: the optional definition field (`apiServerDelegatedTokenFieldsShape`, absent = false) and `doesApiServerAcceptDelegatedTokens(api_server)` — true only for a non-hardcoded definition with the flag set, so the auth server's own API and the `oidc-userinfo` audience never accept delegated tokens (nobody may act for a user against the user's own account), and neither does an unknown API server. Set by `PUT /api/apis/{api_server_id}/delegated-token-policy` (`{ accept_delegated_tokens: boolean }`, strict; the API server's managers per `canUserManageResource` — org owners/admins, the owning user — or platform admins; hardcoded → 403; registry `setApiServerDelegatedTokenPolicy()`); creation refuses `accept_delegated_tokens: true` with 400 (`create.operation.ts`), so the PUT is the only way in. Client SDK: `setApiServerDelegatedTokenPolicy(api_server_id, accept)` (auth-server app only, like the other management writes). UI: `ApiServerDelegatedTokensCard` (`auth-server/src/components/ApiServerDelegatedTokens/`, `data-testid` `api-server-delegated-tokens-card` / `accept-delegated-tokens-switch`) on `/apis/[api_server_id]` for non-hardcoded servers. Managers turn it on once their resource server runs auth-server-sdk ≥ 0.39.0 (jwt ≥ 0.16.0).

**Issuance gate.** `issueOidcTokens({ actor })` (`auth-server/src/lib/oidc/issue-oidc-tokens.ts`) calls `assertDelegatedTokenIssuance()` (`delegated-token-issuance.ts`, unit-tested with an injected loader) before minting anything: the access token must come ALONE — `issue_refresh_token: false` and no id_token (TypeError otherwise: a refresh token cannot carry `act`, so refreshing it would mint plain user tokens and launder the delegation away) — and the access token's API server (`access_token_audience_api_server_id`, or the audience mapped by `getApiServerIdForTokenAudience`) must pass `doesApiServerAcceptDelegatedTokens()`, else `DelegatedTokensNotAcceptedError` (`@/lib/error/`), which a grant answers with `invalid_target` (RFC 8693 §2.2.2). The actor then flows through `generateTokensForAuthenticatedUser({ actor })` and `generateAccessToken({ actor })` into `JWT_Factory.access()`; never call those two with an actor directly.

**Not there yet.** No grant passes `actor`: the planned emitter is an RFC 8693 token-exchange grant at `POST /api/oidc/token` (`grant_type=urn:ietf:params:oauth:grant-type:token-exchange`) for confidential clients, whose actor would be the client's service account (`client-credentials-grant` skill) acting for the user of a `subject_token` issued to that client, with a narrowed `scope` and a `resource` that accepts delegated tokens. It will also need: `token_exchange` as an `IssuedTokenGrantType`, a decision on agent-session refresh (server-side delegation record, since refresh tokens cannot carry `act`), discovery `grant_types_supported`, and the user-facing view of agent sessions. Revoking delegated tokens works like any other (RFC 7009 / logout, by `jti` and `refresh_jti`).
