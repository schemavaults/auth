# Client SDK Token Flows (openid-client)

`@schemavaults/auth-client-sdk` redeems authorization codes and refresh tokens at the **standard OIDC token endpoint** (`POST /api/oidc/token`, form-encoded) through the `openid-client` package (`packages/auth-client-sdk/src/lib/oidc/`): the SDK builds its `openid-client` `Configuration` from `auth_server_url` + `buildOidcProviderMetadata()` (`@schemavaults/auth-common`, `src/oidc/provider-metadata.ts` — the SAME function the server serves at `/.well-known/openid-configuration` and, for plain OAuth 2.0 clients such as MCP clients, at the RFC 8414 path `/.well-known/oauth-authorization-server` — both rewritten in `next.config.ts` to `/api/oidc/openid-configuration` — via `buildOidcDiscoveryDocument()`, so the SDK cannot drift from the advertised metadata and needs no discovery round trip; endpoint paths come from `OIDC_ENDPOINT_PATHS` next to it), sends HTTP through the adapter's `fetch` (`credentials: "include"` on the token endpoint only), and uses `authorizationCodeGrant()` for redirect callbacks (verifies `state`, RFC 9207 `iss`, PKCE, and the id_token `nonce`) / `genericGrantRequest("authorization_code")` for the auth server's own same-context login (no `redirect_uri`; the SDK checks the id_token `nonce` itself) / `refreshTokenGrant()` or a cookie-authenticated `genericGrantRequest("refresh_token")` for refreshes. `handleSuccessfulAuthentication()` accepts the callback's `iss` as its sixth argument (forwarded by `useTradeAuthorizationCodeForTokensEffect` in the react provider). The legacy JSON endpoints `/api/auth/token/{authorization_code,refresh_token}/[client_app_id]` are **deprecated** and kept only for SDK versions < 0.18 still deployed; remove them once no such clients remain.

Two extensions let the SDK use the spec endpoint without the legacy response shape (wire contract in `packages/auth-common/src/oidc/token-endpoint-extensions.ts`, server parsing in `auth-server/src/lib/oidc/token-request-extensions.ts`):
- **RFC 8707 `resource`**: mints the response's single `access_token` for that audience (auth server URL or API server id, authorized via `validateAudience`) instead of the reserved `oidc-userinfo` audience; one `resource` per token request (more → `invalid_target`). The SDK sends its first default audience on the code grant and acquires further default audiences through follow-up refresh grants (each rotating the refresh token); `acquireAccessToken()` fetches other audiences on demand.
- **`refresh_token_delivery=http_only_cookie`**: the endpoint sets the `refresh_token_<client_id>` HTTP-only cookie + `refresh_token_expiry_<client_id>` marker (`setRefreshTokenCookieOnResponse`) and omits `refresh_token` from the JSON body (RFC 6749 §5.1 makes it OPTIONAL); forced for the auth server's own app, honored for other apps only in secure environments (`resolveRefreshTokenDeliveryMode`), else inlined. A refresh grant without a `refresh_token` form field falls back to that cookie. Every successful response carries `refresh_token_expires_in` (seconds). The SDK requests cookie delivery iff the adapter's `doesSupportHttpOnlyRefreshToken()` is true.

Token responses carry identity claims only, so the SDK syncs the platform's full `UserData` from `GET /api/auth/whoami/[client_app_id]` (now database-backed via `loadUserData`, authenticated by the refresh cookie or a `Bearer` refresh token) after every login and refresh. The token endpoint applies per-client-app credentialed CORS (`validateCorsForClientApp`) when an `Origin` header is present (unregistered origins get a 403 before any grant work) and the wildcard allowance otherwise, rate-limits refresh grants per IP like the legacy endpoint, and treats `redirect_uri` as required only when the authorization request carried one (RFC 6749 §4.1.3). E2E helpers (`cy.login()`/`cy.register()`) intercept `**/api/oidc/token`.
