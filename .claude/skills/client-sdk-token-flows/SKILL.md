# Client SDK Token Flows (openid-client)

`@schemavaults/auth-client-sdk` redeems authorization codes and refresh tokens at the **standard OIDC token endpoint** (`POST /api/oidc/token`, form-encoded) through the `openid-client` package (`packages/auth-client-sdk/src/lib/oidc/`): the SDK builds its `openid-client` `Configuration` from `auth_server_url` + `buildOidcProviderMetadata()` (`@schemavaults/auth-common`, `src/oidc/provider-metadata.ts` — the SAME function the server serves at `/.well-known/openid-configuration` and, for plain OAuth 2.0 clients such as MCP clients, at the RFC 8414 path `/.well-known/oauth-authorization-server` — both rewritten in `next.config.ts` to `/api/oidc/openid-configuration` — via `buildOidcDiscoveryDocument()`, so the SDK cannot drift from the advertised metadata and needs no discovery round trip; endpoint paths come from `OIDC_ENDPOINT_PATHS` next to it; the one deployment-dependent member, RFC 7591 `registration_endpoint`, is added by the server only while `allow_dynamic_client_registration` is on and is never part of the SDK's static copy), sends HTTP through the adapter's `fetch` (`credentials: "include"` on the token endpoint only), and uses `authorizationCodeGrant()` for redirect callbacks (verifies `state`, RFC 9207 `iss`, PKCE, and the id_token `nonce`) / `genericGrantRequest("authorization_code")` for the auth server's own same-context login (no `redirect_uri`; the SDK checks the id_token `nonce` itself) / `refreshTokenGrant()` or a cookie-authenticated `genericGrantRequest("refresh_token")` for refreshes. `handleSuccessfulAuthentication()` accepts the callback's `iss` as its sixth argument (forwarded by `useTradeAuthorizationCodeForTokensEffect` in the react provider). `POST /api/oidc/token` is the platform's only token endpoint: the pre-OIDC JSON endpoints `/api/auth/token/{authorization_code,refresh_token}/[client_app_id]` (and their `createAuthorizationCodePOSTBodySchema`/`createRefreshTokenPOSTBodySchema` body schemas in `@schemavaults/auth-common`) were removed once every client ran SDK ≥ 0.18.

Two extensions let the SDK use the spec endpoint without a bespoke response shape (wire contract in `packages/auth-common/src/oidc/token-endpoint-extensions.ts`, server parsing in `auth-server/src/lib/oidc/token-request-extensions.ts`):
- **RFC 8707 `resource`**: mints the response's single `access_token` for that audience (auth server URL, API server id, or — since dynamic client registration — the https URL of a registered API server, resolved through its domains per the server's `resource_url_match_mode` and minted with `aud` = the URL verbatim; see the `dynamic-client-registration` skill; authorized via `validateAndResolveAudiences`) instead of the reserved `oidc-userinfo` audience; one `resource` per token request (more → `invalid_target`). The SDK sends its first default audience on the code grant and acquires further default audiences through follow-up refresh grants (each rotating the refresh token); `acquireAccessToken()` fetches other audiences on demand.
- **`refresh_token_delivery=http_only_cookie`**: the endpoint sets the `refresh_token_<client_id>` HTTP-only cookie + `refresh_token_expiry_<client_id>` marker (`setRefreshTokenCookieOnResponse`) and omits `refresh_token` from the JSON body (RFC 6749 §5.1 makes it OPTIONAL); forced for the auth server's own app, honored for other apps only in secure environments (`resolveRefreshTokenDeliveryMode`), else inlined. A refresh grant without a `refresh_token` form field falls back to that cookie. Every successful response carries `refresh_token_expires_in` (seconds). The SDK requests cookie delivery iff the adapter's `doesSupportHttpOnlyRefreshToken()` is true. The React provider's `ReactAuthClientSdkAdapter` answers true only for the auth server's own app and for an app with same-origin auth session routes (below), in every environment. It never puts a client app's refresh token in the auth server's cookie: for a page on another site that cookie is a third-party cookie, which WebKit (Safari, every iOS browser) drops: the code exchange succeeded but whoami then answered 401 ("Did not receive user data from auth server after login"). Without session routes client apps keep the (rotating) refresh token in localStorage, present it as `Authorization: Bearer` to whoami (with `credentials: "omit"`, so a cookie left by an older SDK cannot shadow it) and revoke it on logout through `POST /api/auth/logout/[client_app_id]` with the same Bearer (the endpoint revokes the app's cookie and/or a Bearer refresh token issued to that app). A refresh grant that presents its refresh token as the app's cookie (no `refresh_token` form field) always gets the rotated token back as the cookie, never inline, whatever it requested (`resolveRefreshTokenDeliveryMode`'s `presented_via_cookie`): otherwise a page script could make the browser send the HTTP-only cookie and read the new refresh token from the body.

**Same-origin auth session routes** (the default for apps generated by `auth-server-sdk codegen`): one route handler per route from `@schemavaults/auth-server-sdk/auth-session-route` (`packages/auth-server-sdk/src/auth-session-route/`: `createAuthSessionTokenRoute()` → `{ POST }`, `createAuthSessionWhoamiRoute()` → `{ GET }`, `createAuthSessionLogoutRoute()` → `{ POST }`, sharing `createSessionRoute()` in `session-route-context.ts`), generated at `auth/session/{token,whoami,logout}/route.ts`. The client SDK takes each route's URL separately: `AuthSessionRoutes` (`{ token, whoami, logout }`, `packages/auth-client-sdk/src/types/AuthSessionRoutes.ts`) from the adapter's `getSessionRouteUrls()` (`packages/auth-client-sdk/src/lib/session-route.ts`, which also exports codegen's `AUTH_SESSION_ROUTE_PATHS`), set through `session_routes` on `<AuthProvider>` (paths or absolute URLs; → `AuthClientFactory` → `ReactAuthClientSdkAdapter`), which the generated `auth-provider.tsx` sets to `AUTH_SESSION_ROUTE_PATHS` (`null` opts out). The SDK then sends token-endpoint requests to `token` (rewritten in `createOidcClientConfiguration`'s `customFetch`, `credentials: "same-origin"`), whoami to `whoami` and logout to `logout`. The routes forward them to the auth server server-to-server (inline delivery; the browser's `Origin` is forwarded), keep the refresh token in a `[__Secure-]schemavaults_refresh_token_<app>` cookie (HttpOnly, `SameSite=Strict`, `Path`: the routes' common parent path derived from the request URL, or the factories' `cookie_path` option for routes that share no parent) on the app's own domain, strip `refresh_token` from every response body, present it as `Bearer` to whoami / logout, and refuse cross-origin requests (the token route also other apps and other grant types). To the SDK it is the HTTP-only-cookie mode (the JS-readable `refresh_token_expiry_<app>` marker on the app's domain still tracks the session). Its logout also best-effort revokes a session an older SDK left in the auth server's cookie. Known limit: refresh grants proxied through the token route count against the app server's IP in the auth server's per-IP rate limit.

Token responses carry identity claims only, so the SDK syncs the platform's full `UserData` from `GET /api/auth/whoami/[client_app_id]` (now database-backed via `loadUserData`, authenticated by the refresh cookie or a `Bearer` refresh token) after every login and refresh. The token endpoint applies per-client-app credentialed CORS (`validateCorsForClientApp`) when an `Origin` header is present (unregistered origins get a 403 before any grant work) and the wildcard allowance otherwise, rate-limits refresh grants per IP, and treats `redirect_uri` as required only when the authorization request carried one (RFC 6749 §4.1.3). E2E helpers (`cy.login()`/`cy.register()`) intercept `**/api/oidc/token`.
