# Client SDK Token Flows (openid-client)

`@schemavaults/auth-client-sdk` redeems authorization codes and refresh tokens at the **standard OIDC token endpoint** (`POST /api/oidc/token`, form-encoded) through the `openid-client` package (`packages/auth-client-sdk/src/lib/oidc/`): the SDK builds its `openid-client` `Configuration` from `auth_server_url` + `buildOidcProviderMetadata()` (`@schemavaults/auth-common`, `src/oidc/provider-metadata.ts` — the SAME function the server serves at `/.well-known/openid-configuration` and, for plain OAuth 2.0 clients such as MCP clients, at the RFC 8414 path `/.well-known/oauth-authorization-server` — both rewritten in `next.config.ts` to `/api/oidc/openid-configuration` — via `buildOidcDiscoveryDocument()`, so the SDK cannot drift from the advertised metadata and needs no discovery round trip; endpoint paths come from `OIDC_ENDPOINT_PATHS` next to it; the one deployment-dependent member, RFC 7591 `registration_endpoint`, is added by the server only while `allow_dynamic_client_registration` is on and is never part of the SDK's static copy), sends HTTP through the adapter's `fetch` (`credentials: "include"` on the token endpoint only), and uses `authorizationCodeGrant()` for redirect callbacks (verifies `state`, RFC 9207 `iss`, PKCE, and the id_token `nonce`) / `genericGrantRequest("authorization_code")` for the auth server's own same-context login (no `redirect_uri`; the SDK checks the id_token `nonce` itself) / `refreshTokenGrant()` or a cookie-authenticated `genericGrantRequest("refresh_token")` for refreshes. `handleSuccessfulAuthentication()` accepts the callback's `iss` as its sixth argument (forwarded by `useTradeAuthorizationCodeForTokensEffect` in the react provider). `POST /api/oidc/token` is the platform's only token endpoint: the pre-OIDC JSON endpoints `/api/auth/token/{authorization_code,refresh_token}/[client_app_id]` (and their `createAuthorizationCodePOSTBodySchema`/`createRefreshTokenPOSTBodySchema` body schemas in `@schemavaults/auth-common`) were removed once every client ran SDK ≥ 0.18.

Two extensions let the SDK use the spec endpoint without a bespoke response shape (wire contract in `packages/auth-common/src/oidc/token-endpoint-extensions.ts`, server parsing in `auth-server/src/lib/oidc/token-request-extensions.ts`):
- **RFC 8707 `resource`**: mints the response's single `access_token` for that audience (auth server URL, API server id, or — since dynamic client registration — the https URL of a registered API server, resolved through its domains per the server's `resource_url_match_mode` and minted with `aud` = the URL verbatim; see the `dynamic-client-registration` skill; authorized via `validateAndResolveAudiences`) instead of the reserved `oidc-userinfo` audience; one `resource` per token request (more → `invalid_target`). The SDK sends its first default audience on the code grant and acquires further default audiences through follow-up refresh grants (each rotating the refresh token); `acquireAccessToken()` fetches other audiences on demand.
- **`refresh_token_delivery=http_only_cookie`**: the endpoint sets the `refresh_token_<client_id>` HTTP-only cookie + `refresh_token_expiry_<client_id>` marker (`setRefreshTokenCookieOnResponse`) and omits `refresh_token` from the JSON body (RFC 6749 §5.1 makes it OPTIONAL); forced for the auth server's own app, honored for other apps only in secure environments (`resolveRefreshTokenDeliveryMode`), else inlined. A refresh grant without a `refresh_token` form field falls back to that cookie. Every successful response carries `refresh_token_expires_in` (seconds). The SDK requests cookie delivery iff the adapter's `doesSupportHttpOnlyRefreshToken()` is true. The React provider's `ReactAuthClientSdkAdapter` answers true for the auth server's own app; for an app with a same-origin auth session route (below); and otherwise, outside development/test, only when the page is on the same site (scheme + registrable domain) as the auth server (`isSameSiteAsAuthServer()` in `packages/auth-react-provider/src/lib/same-site-as-auth-server.ts`, which finds the page's eTLD+1 by probing which suffix of its host the browser accepts as a cookie `Domain`). For a page on another site the cookie set by the token endpoint would be a third-party cookie, which WebKit (Safari, every iOS browser) drops: the code exchange succeeded but whoami then answered 401 ("Did not receive user data from auth server after login"). Without a session route such pages keep the (rotating) refresh token in localStorage, present it as `Authorization: Bearer` to whoami (with `credentials: "omit"`, so a cookie left by an older SDK cannot shadow it) and revoke it on logout through `POST /api/auth/logout/[client_app_id]` with the same Bearer (the endpoint revokes the app's cookie and/or a Bearer refresh token issued to that app). A refresh grant that presents its refresh token as the app's cookie (no `refresh_token` form field) always gets the rotated token back as the cookie, never inline, whatever it requested (`resolveRefreshTokenDeliveryMode`'s `presented_via_cookie`): otherwise a page script could make the browser send the HTTP-only cookie and read the new refresh token from the body.

**Same-origin auth session route** (the default for apps generated by `auth-server-sdk codegen`): `createAuthSessionRouteHandler()` (`packages/auth-server-sdk/src/auth-session-route/`, export `@schemavaults/auth-server-sdk/auth-session-route`), generated at `auth/session/[action]/route.ts` and enabled by `session_route_uri="/auth/session"` in the generated `auth-provider.tsx` (→ `<AuthProvider session_route_uri>` → `AuthClientFactory` → the adapter's `getSessionRouteUrl()`). The SDK then sends token-endpoint requests to `<route>/token` (rewritten in `createOidcClientConfiguration`'s `customFetch`, `credentials: "same-origin"`), whoami to `<route>/whoami` and logout to `<route>/logout` (`packages/auth-client-sdk/src/lib/session-route.ts`). The route forwards them to the auth server server-to-server (inline delivery; the browser's `Origin` is forwarded), keeps the refresh token in a `[__Secure-]schemavaults_refresh_token_<app>` cookie (HttpOnly, `SameSite=Strict`, `Path=<route>`) on the app's own domain, strips `refresh_token` from every response body, presents it as `Bearer` to whoami / logout, and refuses cross-origin requests and other apps' / grant types. To the SDK it is the HTTP-only-cookie mode (the JS-readable `refresh_token_expiry_<app>` marker on the app's domain still tracks the session). Its logout also best-effort revokes a session an older SDK left in the auth server's cookie. Known limit: refresh grants proxied through the route count against the app server's IP in the auth server's per-IP rate limit.

Token responses carry identity claims only, so the SDK syncs the platform's full `UserData` from `GET /api/auth/whoami/[client_app_id]` (now database-backed via `loadUserData`, authenticated by the refresh cookie or a `Bearer` refresh token) after every login and refresh. The token endpoint applies per-client-app credentialed CORS (`validateCorsForClientApp`) when an `Origin` header is present (unregistered origins get a 403 before any grant work) and the wildcard allowance otherwise, rate-limits refresh grants per IP, and treats `redirect_uri` as required only when the authorization request carried one (RFC 6749 §4.1.3). E2E helpers (`cy.login()`/`cy.register()`) intercept `**/api/oidc/token`.
