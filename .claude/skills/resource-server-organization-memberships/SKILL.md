# Organization memberships for resource servers

## Why it is server-side

`GET /api/me/organizations` takes the auth server session. Only the auth server's own app may obtain access tokens for the auth server's audience (`validateAndResolveAudiences()` in `auth-server/src/lib/validate-audience.ts` refuses `auth-server-only` audiences for every other client app, and the client-credentials grant never offers it), because such a token works as a full session on the auth server's API. So the client SDK's `listMyOrganizationMemberships()` (and the react provider's `useMyOrganizations()`) reject with `MyOrganizationMembershipsUnavailableError` on any other app, before requesting a token. A third-party (or first-party but separately registered) app gets "my organizations" from its own backend, which asks the auth server as its API server.

## The two resource-server endpoints

Both authenticate the calling API server with a single-use JWKS access assertion (`Authorization: Bearer <assertion>` signed with the API server's JWKS access key, the API server named in `X-Api-Server-Id`), the same credential as the JWKS download.

- `GET /api/resource-server/organizations/{organization_id}/members/{uid}/role` (`.../members/[uid]/role/operation.ts`): the user's role or `null`. Verifies the assertion inside the handler (its 400-before-401 ordering is pinned by the E2E suite). Access is decided by `getOrganizationMembershipAccess(api_server, organization_id)` from `@schemavaults/app-definitions`: `"owner"` (the API server's own organization; for a platform-owned API server that is the deployment's owner organization) answers as before, no subject token needed; `"granted"` (another organization, API server has `all_organizations`) requires `X-Subject-Token`; `false` is a 403.
- `GET /api/resource-server/users/{uid}/organizations` (`app/api/resource-server/users/[uid]/organizations/operation.ts`): `requireAuth({ schemes: [jwksAccessAssertionScheme] })` (the resolver reads `X-Api-Server-Id`), `X-Subject-Token` always required (400 when missing or malformed, 403 when it does not verify). Answers `{ uid, organization_membership_visibility, memberships }`, the `OrganizationMembershipRoleDetails` of `listUserOrganizationMembershipDetails()` (the `/api/me/organizations` shape, admins' virtual owner-organization membership and service accounts' virtual membership included) filtered to the organizations the API server may see. `Cache-Control: no-store`.

## The subject token

Both endpoints read `X-Subject-Token` through `parseSubjectTokenHeader()` (`auth-server/src/lib/resource-server/subject-token-header.ts`) before using it: `absent`, `malformed` (with a reason) or `token`. Only what can be one of the platform's access tokens passes: a JWE in compact serialization (five non-empty base64url segments), at most `MaximumBrowserCookieSize` (4096) characters since access tokens live in cookies, whose protected header is a JSON object with `alg` = `encrypt_decrypt_alg` (`RSA-OAEP-256`) and non-empty `enc`, `keyset_id` and `aud`; the value is never trimmed. A malformed header is a 400 in the endpoint's `{ success: false, error }` envelope (`ResourceServerBadRequestResponse`); the role endpoint parses it before verifying the assertion and refuses it even for own-organization lookups that would ignore it. The request schemas declare the header as a plain string so the handler owns the decision.

`verifyResourceServerSubjectToken()` (`auth-server/src/lib/resource-server/verify-subject-token.ts`) runs the RFC 7662 introspection pipeline with the calling API server as the caller (`decodeIntrospectableToken` + `isIntrospectedTokenActive`): the token must decrypt with the API server's own keyset (so it was minted for it, by id or by an RFC 8707 resource URL that resolved to it), be an access token, not be revoked or predate the user's `tokens_valid_after`, the user must still authorize the client app and the app must still be connected to the API server; plus its `uid` must equal the path `uid`. A leaked JWKS access key therefore cannot enumerate anyone's memberships outside the API server's own organization: only users actively presenting a token to it. Client-credentials tokens work too (the subject is the app's service account).

## The grant

`API_SERVERS.organization_membership_visibility` (migration 00045, NOT NULL DEFAULT `'owning_organization'`, CHECK constraint) is part of `SchemaVaultsApiServerDefinition` (optional on the wire, `getOrganizationMembershipVisibility()` resolves the default). It is never set at creation: `POST /api/apis` validates its body with the definition schema (so the field is accepted there) and then refuses any value other than `owning_organization` with 400, for platform admins too, and `registerApiServer` inserts an explicit column list as a second line of defence. `ResourceServerOrganizationMembershipVisibility.cy.ts` pins that neither a regular user (organization owner) nor an admin can create a widened API server. Only platform administrators change it: `PUT /api/apis/{api_server_id}/organization-membership-visibility` (`routeGuard: "admin"`, 403 for hardcoded API servers) → `SchemaVaultsApiServerRegistry.setApiServerOrganizationMembershipVisibility()`; client SDK `setApiServerOrganizationMembershipVisibility()`; the `ApiServerOrganizationMembershipCard` on `/apis/[api_server_id]` (switch enabled for platform admins only, `isPlatformAdmin` prop). The API server's own managers cannot widen it: `all_organizations` is for multi-tenant platform services (e.g. the schema registry, which serves every organization).

## Server SDK

- `isUserInOrganization(auth_server_url, api_server_id, key, uid, organization_id, { subject_token?, fetch? })` sends `X-Subject-Token` when given.
- `listUserOrganizations({ auth_server_url, api_server_id, jwks_access_private_key, uid, subject_token, fetch? })` calls the list endpoint and validates the response (including that it is about `uid`).
- `createSchemaVaultsAuthResolvers()` principals carry `getOrganizationRole` and `listOrganizationMemberships` (the latter is declared on `AuthPrincipal` in `@schemavaults/openapi-operations`); both forward the access token the request presented (bearer or `access_token_<api_server_id>` cookie) as the subject token.
