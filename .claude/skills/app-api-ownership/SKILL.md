# App & API Ownership

Client application and API server declarations (`APPS` / `API_SERVERS`, migration `00037`) carry an explicit ownership discriminant instead of the former "NULL `owner_organization_id` means platform-owned" convention: `owner_type` (`'platform' | 'organization' | 'user'`, NOT NULL, CHECK-constrained against the id columns so exactly one owner is recorded), `owner_organization_id` (set only for `organization`), `owner_uid` (set only for `user`; FK → `USERS(uid) ON DELETE CASCADE`), and `created_by` (audit only; FK `ON DELETE SET NULL`). Platform rows keep a NULL owner organization in the database, but the API-facing definition still reports the deployment's virtual owner organization as `owner_organization_id` for backwards compatibility (`ownershipFieldsFromDatabaseRow` in `auth-server/src/lib/ownership/ownership-columns.ts`). The shared model lives in `@schemavaults/app-definitions` (`src/resource-ownership.ts`): the ownership fields are spread into both definition schemas (all optional on the wire so older SDK clients keep working) and **`resolveResourceOwnership(def, { platform_owner_organization_id? })`** is the canonical reader — it honours an explicit `owner_type` and falls back to the legacy interpretation otherwise; browser code passes the platform org id from `useAuthUiOwnerOrganizationId()` (or uses `useResolvedResourceOwnership()` / `<ResourceOwnerLabel />` from `@schemavaults/auth-ui`) because the env var is not available in client bundles. The hardcoded app/API definitions are `owner_type: "platform"`.

*User-owned* resources let any account register its own apps/APIs without belonging to an organization (the mode dynamic client registration will build on). `POST /api/apps` / `POST /api/apis` resolve the requested owner via `resolveRequestedOwnershipForCreation` (`auth-server/src/lib/ownership/requested-ownership.ts`): `owner_type: "user"` (or an `owner_uid`) → owned by the caller (never another account; gated for non-admins by the `allow_user_owned_resource_creation` server setting, default `true`, editable on `/admin/settings`), `owner_type: "organization"` / an `owner_organization_id` → the caller must be an owner/admin of that organization, `owner_type: "platform"` / the platform org id → global admins only, and a body with no ownership fields is platform-owned for admins (the historical admin-console behaviour) and user-owned for everyone else. Authorization on every app/API surface goes through `auth-server/src/lib/ownership/resource-access.ts`: `getUserAccessLevelForResource()` maps ownership to `none | member | admin | owner` (organization role, `owner` for the owning user of a user-owned resource, `owner` for global admins, `none` for non-admins on platform resources) and `canUserViewResource` (member+, or public) / `canUserManageResource` (admin+: domains, callback URLs, client secrets, JWKS access keys) / `isUserOwnerOfResource` (owner: delete, `connect_app`) wrap it (`canUserManageApp` and `hasUserAccessToApiServer`, formerly `isUserInApiOwnerOrganization`, delegate to these). Listing: `list_apps_query_type=owned` / `list_apis_query_type=owned` return the caller's user-owned rows (`listUserOwnedApps` / `listUserOwnedApiServers`), `=accessible` returns everything the caller can reach by ownership — their own rows, rows owned by any organization they belong to, and every row (hardcoded included) for global admins (`listAppsAccessibleToUser` / `listApiServersAccessibleToUser`) — and the `org` query for the platform organization selects `owner_type = 'platform'` rows (user-owned rows also have a NULL owner organization, so the NULL is no longer a selector). The `/apps` and `/apis` pages (`auth-server/src/app/(client)/(authenticated)/{apps,apis}/page.tsx`, linked from the dashboard sidebar; the non-admin counterparts of `/admin/apps` and `/admin/apis`) render `AppsCard` / `ApiServersCard` with `queryType="accessible"` plus an `<OwnerTypeFilter />` in a card-backed toolbar (`@schemavaults/auth-ui`; All / Personal / Organization / Platform-for-admins, applied client-side via `useOwnerTypeFilteredResources` on the row's resolved `owner_type`; the Personal option is hidden via `showPersonal` when the viewer owns no personal rows — read from the same SWR list via the exported `useAppsList` / `useApiServersList` — and cannot create any, and a selection whose option is hidden resets to All). Creating from those pages makes *personal* (user-owned) resources — organization-owned ones are created from the organization page and platform-owned ones from the admin console — and the create dialogs take a `RequestedResourceOwnership` prop derived from the card's query type. Per-row management controls are gated client-side by `useCanManageListedResource` (global admin, the owning user, an org owner/admin on the org page, or — on the accessible list — membership of the page-preloaded `managedOrganizationIds`); the server enforces every action regardless.
