# Plain OAuth 2.1 Grants (no `openid` scope)

`scope` is OPTIONAL on the authorization request (RFC 6749 §3.3). A request that includes `openid` is an OpenID Connect authentication request (id_token + `/api/oidc/userinfo`); a request without it — absent, empty, or naming only scopes the server does not know (unknown scopes are dropped per RFC 6749 §3.3) — is a **plain OAuth 2.1 grant**, which is what OAuth-only clients such as MCP clients send. `validateOidcAuthorizeRequest` accepts it (only a *malformed* `scope` is an `invalid_scope` error) and the authorize bridge forwards no `scope` to `/auth/login`; the login/register pages and `POST /api/auth/{login,register}` / `POST /api/auth/session/generate-authorization-code` treat `scope` as optional, and the granted set is stored as `null` on the `AUTHORIZATION_CODES` row via `serializeOidcScopesOrNull()` (`@schemavaults/auth-common`) — `null` scope = nothing granted. The auth-server's own login form and consent screen (`handle-auth-form-submit.ts`, `AppAuthorizationConsentScreen`) fall back to `DEFAULT_AUTH_SCOPE` only for the account-page flow; a third-party flow without a `scope` is sent with none (the client SDK's `sendAuthenticateRequest` accepts `scope: null` for this), never upgraded to an OpenID grant the client did not ask for. At `POST /api/oidc/token` such a code redeems to access + refresh tokens with **no `id_token`** and **no `scope` field** (the tokens carry no `scope` claim); the refresh grant rotates them the same way and refuses a `scope` re-request that widens into `openid`; introspection reports them `active` without a `scope`; and `/api/oidc/userinfo` refuses their access token with a 403 `insufficient_scope` (RFC 6750 §3.1). The first-party session cookie (`setAuthServerRefreshTokenCookie`) is still minted with the platform default scope when the flow granted none, so a third-party plain OAuth grant never narrows the user's own session.
