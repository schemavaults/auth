# OIDC Confidential Clients & Explicit Callback URLs

Client apps are public clients (PKCE-only) by default; registering a *client secret* makes an app a confidential client. Secrets are stored as SHA-256 digests in the `APP_CLIENT_SECRETS` table (one per app; plaintext shown once at generation/rotation, never persisted — generation/hashing/verification in `auth-server/src/lib/oauth2/client-secret.ts`). When an app has a secret, the token endpoint `/api/oidc/token` requires client authentication on every request (via `client_secret_basic` Basic header or `client_secret_post` form field; failures return RFC 6749 §5.2 `invalid_client` 401s with `WWW-Authenticate`), enforced by `authenticateTokenEndpointClient` in `auth-server/src/lib/oauth2/authenticate-token-endpoint-client.ts`. The discovery document advertises `token_endpoint_auth_methods_supported: ["none", "client_secret_basic", "client_secret_post"]`; PKCE S256 stays mandatory for all clients. Management API: `GET`/`POST`/`PUT`/`DELETE /api/apps/[app_id]/client-secret` (metadata / generate / rotate / remove; org owners/admins or global admins, guarded by `loadAppForManagement`; hardcoded apps excluded).

*Token introspection* (`POST /api/oidc/introspect`: `introspect-handler.ts` only glues HTTP to `auth-server/src/lib/oidc/introspection/` — `client-authentication/` (`parse-introspection-request.ts`, pure: the token and exactly one credential method; `authenticate-introspection-caller.ts` dispatching to `authenticate-client-app.ts` / `authenticate-api-server.ts`), then `caller-visibility.ts` (which tokens each caller may see, pure), `decode-introspectable-token.ts`, `introspected-token-activity.ts` (revocation / consent / connection rules, pure over injected signals) bound to the database by `is-introspected-token-active.ts`, `build-active-introspection-response.ts` (pure), chained by `introspect-oidc-token.ts`) has two kinds of caller, each seeing only its own tokens (anything else is exactly `{ active: false }`): a **confidential client app** (client secret, as above; public apps are refused), which may introspect the OIDC surface's tokens issued to it (`oidc-userinfo`-audience access tokens and refresh tokens, `app` claim = the caller); and an **API server**, authenticating with `private_key_jwt` (RFC 7523 §2.2: `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer` (`OAUTH_JWT_BEARER_CLIENT_ASSERTION_TYPE` in `@schemavaults/auth-common`), `client_assertion` = a JWKS access proof token from `createJwksAccessProofToken()`, `iss` = `sub` = the API server id, `aud` = the issuer, verified by `verifyJwksAccessAssertion` incl. single-use `jti`; an optional `client_id` must equal the `iss`; mixing it with a secret is `invalid_request`), which may introspect the access tokens minted for it: its id or an RFC 8707 resource URL as `aud`, decrypted with its own keyset (keysets are looked up by (audience, keyset id), so another server's tokens fail). Both kinds then get the same revocation checks (disabled account, revoked `jti`, `tokens_valid_after`, the user's authorization of the token's client app); API servers additionally require the client app to still pass the token endpoints' app-to-API connection rule (`isClientAppPermittedForApiServer` in `auth-server/src/lib/validate-audience.ts`), so disconnecting an app deactivates its tokens — except for the auth server's own app, which never has a connection (`SchemaVaultsAppToApiPermissionsRegistry` refuses one) and whose API-server tokens are only ever minted internally (`spoofSuperuserAccessToken`, the superuser token `sendEmailViaMailServer` presents to the mail server): they are active unless revoked by `jti` / `tokens_valid_after`. Active responses carry `sub` (`<auth_server_app_id>|<uid>`) and `uid`. Discovery advertises `introspection_endpoint_auth_methods_supported: ["client_secret_basic", "client_secret_post", "private_key_jwt"]` and `introspection_endpoint_auth_signing_alg_values_supported: ["RS256"]`. Resource servers call it through `introspectToken()` in `@schemavaults/auth-server-sdk`. E2E: `example_resource_server/OidcTokenIntrospection.cy.ts` (client apps) and `ApiServerTokenIntrospection.cy.ts` (API servers).

*Explicit callback URLs* (`APP_CALLBACK_URLS` table, `schemaVaultsAppCallbackUrlRefSchema` in `@schemavaults/app-definitions`) optionally restrict OAuth2/OIDC `redirect_uri` values per app + environment: while none are registered, any path on a registered app domain is accepted (legacy origin matching); once one or more exist for an environment, `redirect_uri` must exactly match a registered URL (RFC 6749 §3.1.2.3 simple string comparison via `isRedirectUriInCallbackAllowlist` in `@schemavaults/auth-common`, URL-normalized, fragments forbidden) — except that a registered **http loopback** URL (`http://127.0.0.1/...` or `http://[::1]/...`, never `localhost`) matches on any port per RFC 8252 §7.3 / OAuth 2.1 §8.4.2, since native apps (CLI, desktop, MCP clients) bind an ephemeral port at runtime; scheme, host, path and query must still match. The origin-fallback tier is unchanged. The switch lives in `isRedirectUriRegisteredForClientApp` (`auth-server/src/lib/oauth2/validate-redirect-uri.ts`), which every code-issuance path and page-render guard funnels through. Management API: `GET`/`POST /api/apps/[app_id]/callback-urls`, `DELETE /api/apps/[app_id]/callback-urls/[ref_id]`. Both features surface on the app detail page via `AppClientSecretCard`/`AppCallbackUrlsCard` (`auth-server/src/components/AppOAuthSecurity/`), the client SDK exposes `listClientApplicationCallbackUrls`/`createClientApplicationCallbackUrl`/`deleteClientApplicationCallbackUrl` and `getClientApplicationSecretMetadata`/`generateClientApplicationSecret`/`rotateClientApplicationSecret`/`deleteClientApplicationSecret`, and the E2E seed route `create-test-nextjs-app` accepts optional `client_secret`/`callback_urls` fields.
