# API Scopes (per-API-server OAuth 2.0 scopes)

**Definitions.** An API server defines its own scope values in `API_SERVER_SCOPES` (migration `00046-api-server-scopes.ts`: `api_server_scope_id` UUID PK, `api_server_id` FK `ON DELETE CASCADE`, `scope`, `description`, `created_at`, `created_by`; `UNIQUE (api_server_id, scope)`). Registry functions live in `auth-server/src/lib/auth-db/apis/api-server-scopes.ts` (`listApiServerScopes`, `listApiServerScopeValues`, `createApiServerScope` — locks the API server row and caps at `MAX_API_SCOPES_PER_API_SERVER` = 100, `ConflictError` on duplicates —, `updateApiServerScopeDescription`, `deleteApiServerScope`). Hardcoded API servers define none. Shared schemas are in `@schemavaults/auth-common` (`src/api-scopes/`): `apiScopeValueSchema` (one RFC 6749 scope-token, ≤128 chars, and never an `OIDC_RESERVED_SCOPES` name — `openid profile email address phone offline_access` — so a granted scope string always splits unambiguously, `partitionGrantedScopes()`), `apiScopeDescriptionSchema` (trimmed, 1–256), `apiServerScopeSchema`, the create/update request schemas and `resourceIndicatorSchema`. Management API (catalogue `src/lib/api/operations/apis.ts`): `GET`/`POST /api/apis/{api_server_id}/scopes`, `PATCH`/`DELETE /api/apis/{api_server_id}/scopes/{api_server_scope_id}`; viewing follows `canUserViewResource` (public API servers: anyone signed in), changes follow `canUserManageResource` (org owners/admins, the owning user, platform admins), access checks in `scopes/scope-access.ts`. The value is immutable (rename = new + delete). UI: `ApiServerScopesCard` (`auth-server/src/components/ApiServerScopes/`) on `/apis/[api_server_id]`, SSR-loaded; client SDK: `listApiServerScopes` / `createApiServerScope` / `updateApiServerScope` / `deleteApiServerScope` (`lib/api-server-scopes.ts`; writes are auth-server-app only like the other management methods).

**Granting (authorization request).** Scopes the platform knows are the OIDC ones (`OIDC_SUPPORTED_SCOPES`) plus the API scopes of the API server the request's RFC 8707 `resource` names. `resolveAuthorizationCodeGrant()` (`auth-server/src/lib/oauth2/api-scopes/`) is the single place that derives a code's grant from the requested `scope` + `resource`: it only looks at `resource` when some requested token is not an OIDC name, resolves it with `resolveGrantResource()` (exactly one value; an API server id or a URL of a registered domain via `resolveTokenAudience`; the client must be permitted for that API server by the token endpoint's own rule, `isClientAppPermittedForApiServer`), and grants `grantRequestedScopes(scope, definedValues)` (request order, unknown values dropped). **Leniency is the backwards-compatibility contract**: the authorize endpoint used to ignore `resource`, so an absent, repeated, malformed, unknown, auth-server or not-permitted `resource` is ignored (no error) and the grant is exactly the old OIDC-only one; only infrastructure failures surface (`server_error` at authorize, 500 elsewhere). The result binds `scope_api_server_id` (null when no API scope was granted) on `AuthorizationCodeGrantContext` / the `AUTHORIZATION_CODES` row / the Redis MFA challenge, and `session_scope` (the OIDC part) is what the auth server's own session cookie gets — a third-party API's scopes never land on it. Every mint surface uses it: `validateOidcAuthorizeRequest` (bridge forwards `scope` with the API scopes and `resource` only when API scopes were granted), `handle_login.ts`, `handle_register.ts` (resolved before the account is created), `handle_mfa_verify.ts` (restores the binding), `POST /api/auth/session/generate-authorization-code` and `AlreadyAuthenticatedOnLoginOrRegisterPage`. The `resource` value rides the login UI like `scope`/`nonce`: `/auth/login` + `/auth/register` pages, `handle-auth-form-submit.ts` (→ `sendAuthenticateRequest(..., resource)` and the `/auth/mfa` params), the consent screen's session-code body, the MFA page, and `AUTHORIZE_FLOW_PARAM_KEYS` (verify-email interstitial). SDK apps request them with `login({ scope, resource })` / `register(...)` (`AuthenticateWithRedirectOptions`).

**Token endpoint.** API scopes are bound to their API server: `splitTokenScopes()` (`token-scopes.ts`, pure, unit-tested) puts them on the ACCESS token only when it is minted for that API server (the token request's `resource` resolves to `scope_api_server_id`), keeps them on the REFRESH token either way, and drops any value the API server no longer defines. `issueOidcTokens({ scope, refresh_token_scope, refresh_token_scope_api_server_id })` threads the split down to `generateRefreshToken`, which stamps the refresh-token-only `scope_api_server_id` claim (`@schemavaults/jwt` payload; emitted only when API scopes are carried, so tokens without them stay decodable by older decoders; `generateJWT` refuses it on access tokens, which resource servers decode with a strict schema). The response's `scope` is the access token's. Code grant: no `resource` → userinfo-audience token with OIDC scopes, exactly as before. Refresh grant: `narrowGrantedScope()` keeps the RFC 6749 §6 rule (grantable values — supported OIDC scopes and the binding's currently defined API scopes — must have been granted, else `invalid_scope`; unknown values dropped). `client_credentials` never grants API scopes (no user consents; waits for per-app allowlists). Introspection reports OIDC + API scopes. Deleting a scope does not revoke issued access tokens; refreshes stop carrying it.

**Enforcement.** Resource servers declare them like OIDC scopes: openapi-operations `requiredScopes` (example: `tests/example-nextjs-resource-server/src/app/api/me/notes/`, `example:notes.read`) or the server SDK's `required_scopes`, whose `evaluateRequiredScopes` accepts any `apiScopeValueSchema` value besides the OIDC scopes (anything else is still `invalid_config`). E2E: `tests/e2e-auth-tests/cypress/e2e/example_resource_server/ApiScopes.cy.ts` (defines and finally deletes the example API server's scopes).
