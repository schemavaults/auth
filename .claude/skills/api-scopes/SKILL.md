# API Scopes (per-API-server OAuth 2.0 scopes)

**Definitions.** An API server defines its own scope values in `API_SERVER_SCOPES` (migration `00046-api-server-scopes.ts`: `api_server_scope_id` UUID PK, `api_server_id` FK `ON DELETE CASCADE`, `scope`, `description`, `created_at`, `created_by`; `UNIQUE (api_server_id, scope)`). Registry functions live in `auth-server/src/lib/auth-db/apis/api-server-scopes.ts` (`listApiServerScopes`, `listApiServerScopeValues`, `createApiServerScope` — locks the API server row and caps at `MAX_API_SCOPES_PER_API_SERVER` = 100, `ConflictError` on duplicates —, `updateApiServerScope` (description and/or `allow_dynamic_clients`), `deleteApiServerScope`; reads select explicit `SCOPE_COLUMNS`, never `selectAll()`). Hardcoded API servers define none. Shared schemas are in `@schemavaults/auth-common` (`src/api-scopes/`): `apiScopeValueSchema` (one RFC 6749 scope-token, ≤128 chars, and never an `OIDC_RESERVED_SCOPES` name — `openid profile email address phone offline_access` — so a granted scope string always splits unambiguously, `partitionGrantedScopes()`), `apiScopeDescriptionSchema` (trimmed, 1–256), `apiServerScopeSchema` (with `allow_dynamic_clients`, migration 00047, default true), the create/update request schemas (update: `description` and/or `allow_dynamic_clients`, at least one) and `resourceIndicatorSchema`. Management API (catalogue `src/lib/api/operations/apis.ts`): `GET`/`POST /api/apis/{api_server_id}/scopes`, `PATCH`/`DELETE /api/apis/{api_server_id}/scopes/{api_server_scope_id}`; viewing follows `canUserViewResource` (public API servers: anyone signed in), changes follow `canUserManageResource` (org owners/admins, the owning user, platform admins), access checks in `scopes/scope-access.ts`. The value is immutable (rename = new + delete). UI: `ApiServerScopesCard` (`auth-server/src/components/ApiServerScopes/`) on `/apis/[api_server_id]`, SSR-loaded; client SDK: `listApiServerScopes` / `createApiServerScope` / `updateApiServerScope` / `deleteApiServerScope` (`lib/api-server-scopes.ts`; writes are auth-server-app only like the other management methods).

**Granting (authorization request).** Scopes the platform knows are the OIDC ones (`OIDC_SUPPORTED_SCOPES`) plus the API scopes of the API server the request's RFC 8707 `resource` names. `resolveAuthorizationCodeGrant()` (`auth-server/src/lib/oauth2/api-scopes/`) is the single place that derives a code's grant from the requested `scope` + `resource`: it only looks at `resource` when some requested token is not an OIDC name, resolves it with `resolveGrantResource()` (exactly one value; an API server id or a URL of a registered domain via `resolveTokenAudience`; the client must be permitted for that API server by the token endpoint's own rule, `isClientAppPermittedForApiServer`), and asks for `grantRequestedScopes(scope, grantable)` (request order, unknown values dropped) where `grantable` is the app's user allowance (`listGrantableApiScopeValues(..., grantee: "user")`, below); the code's `grant` holds only those the user consented to (`uid` option; `null` = no user yet, e.g. the authorize bridge or registration: nothing consented). It also returns `requested_scope` (what the flow asks for: forwarded by the bridge), `requested_api_scopes` and `pending_api_scopes` (asked for, grantable, not consented). **Leniency is the backwards-compatibility contract**: the authorize endpoint used to ignore `resource`, so an absent, repeated, malformed, unknown, auth-server or not-permitted `resource` is ignored (no error) and the grant is exactly the old OIDC-only one; only infrastructure failures surface (`server_error` at authorize, 500 elsewhere). The result binds `scope_api_server_id` (null when no API scope was granted) on `AuthorizationCodeGrantContext` / the `AUTHORIZATION_CODES` row / the Redis MFA challenge, and `session_scope` (the OIDC part) is what the auth server's own session cookie gets — a third-party API's scopes never land on it. Every mint surface uses it: `validateOidcAuthorizeRequest` (bridge forwards `scope` with the API scopes and `resource` only when API scopes were granted), `handle_login.ts`, `handle_register.ts` (resolved before the account is created), `handle_mfa_verify.ts` (restores the binding), `POST /api/auth/session/generate-authorization-code` and `AlreadyAuthenticatedOnLoginOrRegisterPage`. The `resource` value rides the login UI like `scope`/`nonce`: `/auth/login` + `/auth/register` pages, `handle-auth-form-submit.ts` (→ `sendAuthenticateRequest(..., resource)` and the `/auth/mfa` params), the consent screen's session-code body, the MFA page, and `AUTHORIZE_FLOW_PARAM_KEYS` (verify-email interstitial). SDK apps request them with `login({ scope, resource })` / `register(...)` (`AuthenticateWithRedirectOptions`).

**Token endpoint.** API scopes are bound to their API server: `splitTokenScopes()` (`token-scopes.ts`, pure, unit-tested) puts them on the ACCESS token only when it is minted for that API server (the token request's `resource` resolves to `scope_api_server_id`), keeps them on the REFRESH token either way, and drops any value the API server no longer defines. `issueOidcTokens({ scope, refresh_token_scope, refresh_token_scope_api_server_id })` threads the split down to `generateRefreshToken`, which stamps the refresh-token-only `scope_api_server_id` claim (`@schemavaults/jwt` payload; emitted only when API scopes are carried, so tokens without them stay decodable by older decoders; `generateJWT` refuses it on access tokens, which resource servers decode with a strict schema). The response's `scope` is the access token's. Code grant: no `resource` → userinfo-audience token with OIDC scopes, exactly as before. Refresh grant: `narrowGrantedScope()` keeps the RFC 6749 §6 rule (grantable values — supported OIDC scopes and the binding's currently defined API scopes — must have been granted, else `invalid_scope`; unknown values dropped). Both grants feed `splitTokenScopes` the *usable* values, `listUsableApiScopeValues()` (grantable to users ∩ consented by this user), so a withdrawn consent or a tightened allowance takes effect at the next code redemption / refresh; narrowing still checks against every defined value. `client_credentials` (no user consents) grants the requested API scopes in the app's SERVICE-ACCOUNT allowance, only with a `resource` that resolves to the API server (none by default). Introspection reports OIDC + API scopes. Deleting a scope does not revoke issued access tokens; refreshes stop carrying it.

**Per-app allowances ("client grants").** Which of an API server's scopes a connected app may be granted, per app-to-API connection (migration `00047-api-scope-grants-and-consents.ts`): `APP_API_SCOPE_POLICIES` (`restrict_user_scopes`, PK `(client_app_id, api_server_id)`, FK → `APPS_TO_APIS_PERMISSIONS` cascade) and `APP_API_SCOPE_GRANTS` (`grantee` `user` | `service_account`, FK → the connection and the scope, both cascade). A separate policy table instead of a column on `APPS_TO_APIS_PERMISSIONS` because that table is read with `selectAll()` into a strict zod schema (a new column would break token minting on older code during a rolling deploy). `listGrantableApiScopeValues(db, { client_app_id, api_server_id, grantee })` (`auth-db/apis/api-scope-grants.ts`) is the rule: connected app → users may grant every defined scope unless `restrict_user_scopes` (then the `user` grants); the service account gets only its `service_account` grants; an unconnected dynamically registered client (no connection) may be granted, for users only, the scopes with `allow_dynamic_clients` of an API server that allows dynamic clients; anything else gets nothing. `setAppApiScopePolicy` replaces the policy and grants in one transaction (`UnknownApiScopesError` → 400, `AppNotConnectedForScopesError` → 404). API: `GET` / `PUT /api/apis/{api_server_id}/connect_app/{client_app_id}/scopes` (view: manage access to the API server OR the app; update: manage access to the API server). Shared schemas: `appApiScopePolicySchema`, `updateAppApiScopePolicyRequestSchema` (`src/api-scopes/scope-grants.ts`). UI: the ListChecks button per connected app on `/apis/[api_server_id]` opens `AppScopeAllowancesDialog`; SDK: `getAppApiScopePolicy` / `updateAppApiScopePolicy` (write = auth-server app only).

**Per-scope consent.** `USER_APP_SCOPE_CONSENTS` (PK `(uid, client_app_id, api_server_scope_id)`; FK `(client_app_id, uid)` → `AUTHORIZED_APPS` cascade, so removing an app's authorization drops its scope consents; FK → the scope cascade). Registry: `auth-db/api-scope-consents/` (`listConsentedApiScopeValues`, `recordApiScopeConsents` — insert-or-ignore, never removes —, `revokeApiScopeConsent`, `listConnectedAppsForUser`). `describeAppConsentStatus()` (`lib/oauth2/api-scopes/consent-status.ts`) answers "must the consent screen be shown": `!authServerApp && (!authorized || pending_api_scopes > 0)`, so a request without API scopes behaves exactly as before (consent only for an app never authorized). It backs `GET /api/apps/{app_id}/check-authorization` (optional `scope` + `resource` query; the response kept `authorized` and gained `consent_required`, `requested_oidc_scopes`, `api_server`, `granted_api_scopes`, `pending_api_scopes` — `appConsentStatusSchema`), the already-signed-in page, the login form (`getAppConsentStatus` in `handle-auth-form-submit.ts`) and the MFA page (`loadConsentRequirement`). `POST /api/apps/{app_id}/authorize` takes optional `scope`, `resource`, `approved_api_scopes` and, in one transaction, authorizes the app and records consent for the approved values that the request asks for and the app may be granted (others ignored). `AppAuthorizationConsentScreen` lists pending scopes as ticked checkboxes (`consent-api-scope-checkbox`, `data-scope`) and already granted ones read-only (`consent-granted-api-scope`). Because the login / MFA handlers mint the code before the screen is shown, the code holds only the already-consented scopes; when the user approves more, the screen mints a fresh code through `POST /api/auth/session/generate-authorization-code` and resumes with it.

**`prompt`.** `validateOidcAuthorizeRequest` parses `prompt` (space-delimited; `none` combined with anything is `invalid_request`). `prompt=consent` is bridged to `/auth/login?prompt=consent` and forces the consent screen (kept through the verify-email interstitial and the MFA page; `AUTHORIZE_FLOW_PARAM_KEYS` includes it). `prompt=none` is answered by `answerSilentAuthorizeRequest()` (`lib/oidc/`) without UI: no session / disabled user → `login_required`; e-mail gate → `interaction_required`; `consent_required` from `describeAppConsentStatus`; else a code is minted and the client is redirected with `code`, `iss`, `state` (plus the legacy SDK params).

**Third-party access.** `GET /api/me/connected-apps` (apps the user authorized, newest first, never the auth server's own app, with `last_used_at` from issued tokens and the granted API scopes — `connectedAppSchema`); `DELETE /api/me/connected-apps/{app_id}/scopes/{api_server_scope_id}` withdraws one scope and revokes the app's unexpired access tokens for that API server (`revokeAccessTokensIssuedToClientAppForAudience`; refresh tokens keep the claim but stop yielding the scope, see usable values above); `DELETE /api/apps/{app_id}/authorize` removes the app (consents cascade, all its tokens revoked). Page: `/account/connected-apps` (`ConnectedAppsCard`, `auth-server/src/components/ConnectedApps/`), linked from a "Third-party access" card on `/account`. SDK (auth-server frontend only): `listMyConnectedApps`, `revokeMyAppScopeConsent`, `revokeClientApplicationAuthorization` (`lib/connected-apps.ts`).

**Enforcement.** Resource servers declare them like OIDC scopes: openapi-operations `requiredScopes` (example: `tests/example-nextjs-resource-server/src/app/api/me/notes/`, `example:notes.read`) or the server SDK's `required_scopes`, whose `evaluateRequiredScopes` accepts any `apiScopeValueSchema` value besides the OIDC scopes (anything else is still `invalid_config`). E2E (`tests/e2e-auth-tests/cypress/e2e/example_resource_server/`): `ApiScopes.cy.ts` (management, bridge, token grants, client_credentials allowance; its users consent to `example:notes.read` when authorizing the app) and `ApiScopeConsent.cy.ts` (consent, allowances, `prompt`, third-party access, and the consent screen / connected-apps page / allowances dialog UI); both define and finally delete the example API server's scopes.
